# Реестр методов тестирования

Найденный баг стоит дорого один раз. Метод, который ловит весь его класс, стоит столько же —
и дальше работает сам, в любом проекте, до первого коммита задачи.

Здесь лежит пилот такого реестра: три метода, выращенные из трёх настоящих дефектов волны
15 сентября 2026 года. Каждый метод — это запись в `registry.json` плюс детектор, который
**доказан замером**: красный на том коммите, где баг жил, зелёный на том, где его починили,
красный на 2–3 сгенерированных вариантах того же класса и зелёный на отрицательных контролях.
Недоказанный детектор в реестр не попадает.

Позже это уедет в отдельный репозиторий. Пока — внутри `upready-store`, чтобы методы росли
рядом с багами, из которых они берутся.

## Команды

```bash
node tools/test-methods/tm.mjs list                  # все методы таблицей
node tools/test-methods/tm.mjs match --symptom "…"   # какой метод ловит эту жалобу
node tools/test-methods/tm.mjs run all               # прогнать по рабочему дереву
node tools/test-methods/tm.mjs run all --strict      # не прощать baseline
node tools/test-methods/tm.mjs run tm-001 --base <sha>   # прогнать по любому коммиту
node tools/test-methods/tm.mjs verify all            # переиграть доказательства всех методов
pnpm test:methods                                    # юниты + verify + run, одной командой
```

У любой команды есть `--json`. `run` и `verify` выходят с кодом 1 на красном, поэтому вставляются
в приёмку и в CI без обёрток.

`--base <sha>` **не трогает рабочее дерево**: коммит разворачивается `git archive` во временный
каталог, и только нужные ему пути (`scope.paths`). В воркtree, где параллельно работает другая
сессия, checkout был бы прямым вредом.

|---|---|---|---|

### tm-001 — `boot-dep-not-in-runtime-install`

`sharp` стоял в `devDependencies`, а `src/api/tenants/branding/upload/route.ts` импортировал его
на уровне модуля. `medusa build` копирует `apps/backend/package.json` в `.medusa/server/package.json`
дословно, рантайм-стадия ставит зависимости оттуда с `--omit=dev` — пакет в образ не попадал, и
контейнер умирал на первом старте в цикле рестартов. Компилятор, сборка и push были зелёные.

Детектор обходит boot-каталоги Medusa (`src/api`, `src/subscribers`, `src/jobs`, `src/links`,
`src/modules`, `src/workflows`, `src/scripts`, `src/migration-scripts` и `medusa-config.ts`),
собирает импорты **уровня модуля** и требует, чтобы каждый пакет стоял в `dependencies`.
Вторая проверка — платформенная: пакет с per-platform `optionalDependencies` (в локе у них
`cpu:`/`os:`) плюс `--ignore-scripts` в рантайм-установке.

Ленивый `require()` внутри функции не считается: его грузит оператор, а не бут. В репозитории
такой один — `src/scripts/import-cherkashina-reviews.ts` требует `pg` внутри хелпера.

### tm-002 — `owner-field-not-shown`

Панель загружала картинку категории в `metadata.image_url` и обещала владелице: «показывается
плиткой везде, где витрина выводит эту категорию». Живой замер: 0 картинок на `/ru`, `/ru/store`
и на странице категории. Ничего нигде не падало.

Две проверки, потому что у класса два лица:

* `written-never-read` — ключ `metadata.*`, который пишет форма панели, не читает никто: ни витрина,
  ни бэкенд, ни сама панель. Поиск читателя идёт по всем трём приложениям намеренно: `metadata.locale`
  на запросе восстановления пароля читает `apps/backend/src/emails/i18n/locale.ts`, и это контракт,
  а не дефект.
* `owner-data-loses-to-build-defaults` — витрина читает данные владельца и выбрасывает их, если их
  меньше N (N ≥ 2), подставляя вшитые в сборку. Это и есть f16: `if (own.length >= 3) return own`,
  а иначе — список категорий чужого магазина из профиля сборки.

Первая проверка **не ловит** исходный f16: на `c60638b` у `image_url` и `image_alt` читатели были.
Ловит вторая. Метод доказывают на том баге, из которого он вырос, а не на удобном соседе.

### tm-003 — `fixture-in-compiled-tree`

`apps/backend/src/scripts/f12-seed-test-order.ts` — приёмочная фикстура на один заказ, в её же шапке
написано «acceptance fixture ONLY … Never run against a real database». `medusa build` компилирует
`src/` целиком, поэтому следующая сборка образа упала на `TS2322` внутри файла, который продукт
никогда не исполняет, и вся волна правок не доехала до живого хоста.

Детектор ищет под `apps/*/src` файлы, которые называют себя одноразовыми (маркеры в тексте) или
названы как фикстура (`seed-test`, `test-seed`, `fixture`). Юнит-тесты (`*.test.ts`, `*.spec.ts`,
`__tests__/`, `integration-tests/`) исключены: это гейты репозитория, а не одноразовые файлы.

## Как добавить метод

1. **Назови класс, а не место.** «sharp не поставился» — это место. «Модуль, который грузится
   на старте, не установлен в рантайм-образе» — класс. Если формулировка не переносится в чужой
   проект, метода ещё нет.
2. **Заведи детектор** в `detectors/<slug>.mjs`. Он экспортирует `id` и
   `run(root, config) → { status, findings, checked }`, где `root` — корень любого дерева
   (рабочее, развёрнутый коммит, каталог фикстуры), а `findings` — массив
   `{ check, severity, file, line, evidence, message }`. Никаких обращений к git, к сети и к
   рабочему каталогу: детектор читает только то дерево, которое ему дали.
3. **Читай чужой код лексером, а не регуляркой.** `lib/source-view.mjs` гасит комментарии, строки,
   шаблоны и regex-литералы, сохраняя смещения и номера строк. Без него `packages/*` внутри строки
   открывает комментарий на сорок строк вниз, а `metadata.image_url` из доккоммента становится
   «читателем поля». Ключи объектных литералов читаются через `sourceView(src, { keepStrings: true })`
   — комментарии сняты, литералы на месте.
4. **Докажи замером.** В `evidence.redOn` — коммит, где баг жил, с `expectCheck` и `expectFile`;
   в `evidence.greenOn` — коммит починки. В `fixtures/<id>/` — минимум два красных варианта того же
   класса и один зелёный отрицательный контроль. Всё это переигрывает `tm verify <id>`, и оно обязано
   быть зелёным до коммита.
5. **Запиши каждый снятый ложняк** в `evidence.falsePositives` — фразой, из-за которой он был, и
   решением, которое его убрало. В этом реестре их уже четыре, и все четыре нашлись только на
   прогоне по настоящему дереву. Детектор, который никогда не краснел на живом коде, не проверен.
6. **`placement`** — где метод стоит в процессе:
   * `before-task` — гоняется при планировании волны и перед первым коммитом задачи;
   * `acceptance` — приёмщик гоняет перед мержем PR;
   * `after-deploy` — гоняется по живому стенду после деплоя.

## `baseline` — как вносить метод в живой репозиторий

Новый детектор почти всегда краснеет на уже существующем коде. Заглушить его, ослабив проверку, —
худшее, что можно сделать: метод перестанет ловить класс ровно там, где класс живёт.

Поэтому у метода есть `baseline` — поимённый список находок, которые репозиторий сегодня терпит.
У каждой записи обязателен `reason` (почему не чинится здесь) и `task` (кто чинит). Такая находка
печатается как `known` и код возврата не портит; **любая новая** находка того же метода делает
прогон красным. `--strict` обнуляет baseline и показывает всё. `tm verify` всегда строгий: baseline
не имеет права прятать фикстуру, которая обязана краснеть.

Сегодня в baseline четыре записи — все четыре найдены этим же пилотом и все четыре настоящие:
одна по `tm-002` (`metadata.language`) и три по `tm-003` (`f12`, `t13`, `t17`).

## Раскладка

```text
tools/test-methods/
├── tm.mjs                  CLI: list / match / run / verify
├── registry.json           сами методы: класс, симптом, детектор, scope, фикстуры, доказательства, baseline
├── detectors/              по файлу на метод
├── fixtures/<id>/          варианты класса (красные) и отрицательные контроли (зелёные)
├── lib/
│   ├── source-view.mjs     лексер: гасит комментарии/строки/шаблоны/regex, сохраняя смещения
│   ├── tree.mjs            git archive любого коммита во временный каталог
│   └── walk.mjs            обход файлов дерева
└── __tests__/              юниты CLI, реестра и разборных частей детекторов
```

## Чего эти методы не делают

* Все три детектора **статические**. Они читают исходники и лок, не запускают ни сборку, ни стенд.
  `tm-001` не заменяет `apps/backend/scripts/verify-runtime-modules.mjs` — тот требует модули из уже
  собранного образа и стоит в `docker build`; статический детектор ловит тот же класс на пять минут
  раньше, ещё до сборки.
* `tm-002` судит по коду, а не по экрану. Он не отвечает на вопрос «а красиво ли нарисовано» — на
  него отвечает живая приёмка (правило 18f).
* Область каждого метода привязана к раскладке этого репозитория через `config` в `registry.json`.
  Перенос в другой проект — это правка `config` и `scope`, а не правка детектора.
