## 2. Архитектура: одно ядро `marketplace`, адаптеры на площадку

### 2.0 Почему ядро, а не два независимых модуля
Три причины, каждая измерена выше, а не выдумана:
1. **Экраны владельца общие.** «Единая лента заказов», «таблица цен и остатков», «отзывы» — по строкам
   матрицы это ОДИН экран на две площадки. Если нормализации нет, каждый экран пишется дважды и расходится.
2. **Связь с каталогом одна.** Наш SKU = `vendorCode` у WB = `offer_id` у Ozon (дайджест магазина:
   «SKU уникальны (артикулы WB/Ozon либо PL-NN)»). Логика сопоставления одна на обе площадки.
3. **Инвариант чтения один.** Реестр разрешённых чтений, единственная точка I/O, fetch-шпион и репо-линт —
   это один набор правил, который должен применяться к КАЖДОМУ адаптеру автоматически, а не копироваться
   руками. Скопированное правило — это правило, которое третий адаптер забудет (правило 20).

```text
  route.ts             # GET: список подключений и их состояние
  [marketplace]/status/route.ts
apps/backend/src/jobs/marketplace-sync.ts      # планировщик
apps/tenant-panel/src/routes/settings/marketplaces/   # раздел «Маркетплейсы»
```

**Что переезжает, а что остаётся.** Модуль `wb` **не переписывается и не переименовывается**: файлы
`endpoints.ts`, `transport.ts`, `sync.ts`, `token.ts`, модели `wb_*` остаются на месте и продолжают быть
единственной точкой I/O к WB. Добавляется один файл `adapter.ts`, который выставляет уже написанное под
общий контракт. Переезжает только внешняя поверхность:

| было (PR #71) | станет | что делать со старым |
|---|---|---|
| `GET /tenants/wb/status` | `GET /tenants/marketplaces/wb/status` | старый маршрут остаётся и отвечает тем же телом ещё одну волну — панель обновляется в том же PR, но ломать чужой вызов нельзя |
| панель `/settings/wildberries` | раздел `/settings/marketplaces`, вкладка «Wildberries» | старый путь редиректит на новый |
| скрипт `wb-sync.ts` | `marketplace-sync.ts --marketplace wb --kind …` | `wb:sync` остаётся алиасом |
| таблицы `wb_*` | остаются как СЫРОЙ слой | `mp_*` — производный слой, считается из `wb_*`/`ozon_*`, а не вместо них |

Сырьё сохраняем отдельно от нормализованного намеренно: `raw` — это то, что реально ответила площадка,
и когда нормализация окажется неверной, пересчитать можно без повторного похода в API (и без нового
расхода лимита).

### 2.2 Контракт адаптера

```ts
// modules/marketplace/contract.ts
export type MarketplaceId = "wb" | "ozon";

/** Одно разрешённое ЧТЕНИЕ. Точь-в-точь строение WbReadEndpoint из PR #71. */
export type ReadEndpoint = {
  id: string;                 // стабильный id: его называют sync и журнал
  host: string;               // полный хост, обязан оканчиваться на один из hostSuffixes адаптера
  method: "GET" | "POST";     // берётся ИЗ ЗАПИСИ, вызывающий его не передаёт
  path: string;               // с плейсхолдерами :name
  docUrl: string;             // страница документации + якорь
  summary: string;            // заголовок метода в документации
  readViaPost?: { docUrl: string; reason: string };  // обязателен и только для POST
  timeoutMs?: number;         // только по измерению, не по вкусу
};

export type MarketplaceAdapter = {
  id: MarketplaceId;
  label: string;                                   // «Wildberries» / «Ozon»
  hostSuffixes: readonly string[];                 // [".wildberries.ru"] / ["api-seller.ozon.ru"]
  endpoints: readonly ReadEndpoint[];              // реестр, default deny
  /** ЕДИНСТВЕННАЯ точка сетевого I/O адаптера. Нет ни fetch, ни baseUrl, ни raw-хелпера. */
  read: <T>(endpointId: string, options: ReadOptions) => Promise<ReadResult<T>>;
  /** Что ключ говорит о себе САМ: срок, область, признак только-чтения — с ссылкой на документ. */
  inspectCredentials: (secret: unknown) => Promise<CredentialFacts>;
  syncKinds: readonly string[];                    // wb: cards|prices|stocks|orders|feedbacks
  runSync: (deps: SyncDeps, kind: string) => Promise<SyncOutcome>;
  /** Сырьё этой площадки → строки mp_*. Чистые функции, без I/O. */
  normalize: {
    products: (rows: unknown[]) => MpProductDraft[];
    offers: (rows: unknown[]) => MpOfferDraft[];
    orders: (rows: unknown[]) => MpOrderDraft[];
    reviews: (rows: unknown[]) => MpReviewDraft[];
    questions: (rows: unknown[]) => MpQuestionDraft[];
  };
};

export type CredentialFacts = {
  set: boolean;
  last4: string | null;
  expiresAt: string | null;
  /** true | false | "unknown" — "unknown" законно, выдумка — нет (правило 17a). */
  readOnly: boolean | "unknown";
  readOnlySource: string | null;   // URL документа, из которого взят вывод
  scopes: { name: string; granted: boolean }[];
  raw: Record<string, unknown>;    // безопасные к показу поля; сам ключ — никогда
};
```

`inspectCredentials` — не украшение: у обеих площадок есть документированный способ спросить у ключа
его собственную область, и оба разные:
- **WB** — разбор JWT без проверки подписи (`token.ts`, уже написан): `exp`, `t`, `sid`, маска `s`,
  бит 30 = «Read only token» (таблица в разделе 0).
- **Ozon** — сетевой вызов `POST /v1/roles`, ответ `{ expires_at, roles: [{ name, methods: [...] }] }`
  (`docs.ozon.ru/api/seller/#operation/AccessAPI_RolesByToken`). Он же — самый честный ответ на вопрос
  «а этот ключ вообще может писать»: в ответе стоит СПИСОК методов ключа. Признак `readOnly` для Ozon
  вычисляется так: `readOnly = true`, только если ни один метод из `roles[].methods` не совпадает с
  нашим deny-list мутаций; иначе `false`. Если ответ не получен — `"unknown"`, и это нормально.

### 2.3 Нормализованный слой `mp_*`

Ключ всюду `(tenant_id, marketplace, external_id)`. Все таблицы несут `source_row_id` — id строки
сырого зеркала, из которой посчитаны, и `synced_at`.

| таблица | что | поля (существенные) |
|---|---|---|
| `mp_product` | карточка площадки | `tenant_id, marketplace, external_id` (WB `nmID`, Ozon `product_id`), `vendor_code` (WB `vendorCode`, Ozon `offer_id`), `sku_external` (Ozon `sku`), `title, brand, category_name, photos jsonb, attributes jsonb, mp_updated_at` |
| `mp_offer` | цена и остаток по складу | `tenant_id, marketplace, external_id, vendor_code, size_external` (WB `chrtID`/`sizeID`), `warehouse_id, warehouse_name, price, discount_price, currency, stock, reserved, measured_at` |
| `mp_order` | заказ/отправление | `tenant_id, marketplace, external_id` (WB `srid`/`orderId`, Ozon `posting_number`), `scheme` (`FBS\|FBO\|DBS\|rFBS`), `status, status_changed_at, ordered_at, buyer_region, warehouse_name, total, currency, is_cancelled` |
| `mp_order_line` | позиция заказа | `order_id, vendor_code, external_id, qty, price, discount` |
| `mp_review` | отзыв | `tenant_id, marketplace, external_id, vendor_code, rating, text, pros, cons, author, created_at, is_answered, answer_draft, answer_draft_at` |
| `mp_question` | вопрос | то же + `question_text, answer_draft` |
| `mp_link` | связь с товаром магазина | `tenant_id, marketplace, external_id, product_id, variant_id, matched_by` (`vendor_code\|manual`), `confidence, linked_at` |
| `mp_sync_run` | один прогон | `tenant_id, marketplace, kind, status, started_at, finished_at, rows, requests, error` |
| `mp_api_call` | журнал вызовов | `tenant_id, marketplace, sync_run_id, endpoint_id, host, method, path, status, ms, error, fetched_at` |

**Почему `mp_offer`, а не «цена в товаре».** У WB цена живёт на размере (`chrtID`), остаток — на паре
(склад, размер). У Ozon цена на `product_id`, остаток — на паре (склад, `sku`), причём складов FBO и FBS
несколько. Одна строка «товар» эти данные не удержит, а «таблица цен и остатков» из строки 4 матрицы —
это ровно проекция `mp_offer`.

**`mp_api_call` и `mp_sync_run` — общие, а не на площадку.** Журнал вызовов существует, чтобы приёмщик
одним запросом доказал: из процесса ушли ТОЛЬКО зарегистрированные чтения. Два журнала — это два запроса
и одна забытая площадка. Таблицы `wb_sync_run` / `wb_api_call` из PR #71 переносятся в `mp_*` миграцией
с `marketplace = 'wb'` (данные не теряются), старые таблицы удаляются отдельным шагом после приёмки.

### 2.4 Связь карточки площадки с товаром магазина
Автоматически — по артикулу: `mp_product.vendor_code` → `product_variant.sku` в пределах тенанта.
Три исхода, и все три видимы владельцу:
- **однозначно** → пишется `mp_link` с `matched_by = 'vendor_code'`;
- **не нашлось** → строка в списке «не связано», кнопка ручной привязки;
- **нашлось несколько** → НЕ связываем автоматически, показываем выбор. Молча взять первый — это
  подстановка значения вместо отсутствия (правило 20a).

Ноль связей — это ошибка настройки, а не пустой экран: если после прогона `mp_link` пуст, а `mp_product`
непуст, экран пишет «сопоставление не сработало: 0 из N», а не «нет данных».

### 2.5 Инвариант «только чтение» как правила в коде

Пять поясов, четыре из них уже стоят в модуле `wb` и обобщаются на ядро:

1. **Реестр с default deny.** Вызов называет `endpointId`, не метод и не URL. Незарегистрированный id →
   исключение ДО открытия сокета. Общий валидатор `guards.ts` вызывается при загрузке каждого адаптера.
2. **Валидатор реестра.** `PUT/PATCH/DELETE` зарегистрировать нельзя — процесс падает на старте.
   Хост обязан оканчиваться на `hostSuffixes` адаптера. Каждая запись обязана нести `docUrl`.
3. **Двойная бухгалтерия POST.** Каждый POST обязан нести `readViaPost.docUrl` + `reason` (цитата из
   документации), и тот же список POST-id продублирован РУКАМИ в тесте. Добавил POST — суите красно,
   пока человек не впишет id туда же.
   *У Ozon это не исключение, а норма: 461 метод из 467 — POST. Значит для Ozon двойная бухгалтерия
   покрывает весь реестр, и это осознанная цена.*
4. **Deny-list мутаций как второй пояс.** Явный список путей, которые документация называет записью
   (`/v1/product/import*`, `/v2/products/stocks`, `/v1/review/comment/create`, `/v1/question/answer/*`,
   `/v2/review/change-status`, `/api/v1/feedbacks/answer`, `/api/v3/stocks/:id` c не-POST, `/api/v3/supplies`
   c POST, …). Запись реестра, попадающая в deny-list, валит загрузку модуля. Пояс нужен ровно потому,
   что у обеих площадок один путь бывает и чтением, и записью, и опечатка в глаголе не видна глазом.
5. **Репо-линт единственной точки вызова.** Скан `apps/backend/src`, `apps/storefront/src`,
   `apps/tenant-panel/src`: имя хоста площадки внутри `fetch(`/`axios`/`request(` допустимо только в
   `transport.ts` своего адаптера. Обобщается: линт берёт хосты из `registry.ts`, поэтому третий адаптер
   попадает под правило автоматически, без правки теста.

Плюс **общий конформанс-тест**: `adapters-conform.unit.spec.ts` прогоняет по КАЖДОМУ адаптеру из
`registry.ts` один и тот же набор: fetch-шпион на `PUT/PATCH/DELETE` и на чужой хост (0 вызовов),
валидатор реестра, deny-list, наличие `docUrl` у всех записей, отсутствие экспорта `fetch`/baseUrl.
Новый адаптер, не прошедший набор, валит суиту самим фактом появления в реестре.

### 2.6 Планировщик
`apps/backend/src/jobs/marketplace-sync.ts` — по одному расписанию на (тенант × площадка × вид):
- карточки и цены — раз в час; остатки — раз в 15 минут; заказы — раз в 10 минут; отзывы и вопросы —
  раз в 30 минут; аналитика — раз в сутки (у Ozon `/v1/analytics/data` жёстко 1 раз в минуту);
- одновременно для одного тенанта и одной площадки бежит один прогон: вторая попытка видит `running`
  прогон и выходит. Иначе два прогона делят один лимит и оба получают 429;
- 429 — уважается `Retry-After` / `X-Ratelimit-Retry`, backoff ограничен сверху (в `wb/transport.ts`
  это уже так: не больше 30 с), после трёх попыток прогон помечается `failed` с текстом ошибки;
- **прогон, который не случился, обязан быть виден**: строка `mp_sync_run` со `status='failed'`
  и сообщением, а не пропущенная запись (правило 20a — «ноль это не пусто»).

### 2.7 Панель: раздел «Маркетплейсы»
Один раздел `/settings/marketplaces` (Geist, канон `~/upready/packages/geist-kit`), внутри — карточка на
площадку, строение повторяет существующую страницу «Wildberries» (`wb-read-only-badge`, `wb-endpoint-table`,
`wb-sync-table` становятся общими `mp-*` компонентами):
- **состояние подключения**: ключ задан (последние 4 символа), до какой даты действует, признак
  «только чтение» со ссылкой на документ либо честное «неизвестно»;
- **область ключа**: список категорий/ролей с отметкой «есть/нет» — из `inspectCredentials`;
- **последняя синхронизация по видам**: когда, сколько строк, сколько запросов, статус, текст ошибки;
- **реестр разрешённых чтений**: метод, путь, ссылка на документацию — чтобы владелец видел, что мы
  умеем спрашивать, и убедился, что писать нечего;
- предупреждение, когда до истечения ключа меньше 14 дней (у Ozon ключ живёт 3 месяца — это будет
  регулярная операция, а не разовая).

### 3.2 Какие права нужны ключу
Документация (`docs.ozon.ru/api/seller/`, раздел «Авторизация через API-ключ») говорит: при создании
ключа выбирается **название**, **уровень доступа** и **цель использования** (личное пользование либо

Что известно точно:
- фактические права ключа отдаёт `POST /v1/roles`: `{ expires_at, roles: [{ name, methods: [...] }] }`.
  В примере документации роли названы `Admin` и `Posting FBS` — то есть роли именованные и у каждой свой
  список методов;
- **срок действия ключа — 3 месяца**, дата в `expires_at` того же метода. Это операционное следствие:
  ключ придётся менять четыре раза в год, и панель обязана предупреждать заранее (раздел 2.7).

**Есть ли у Ozon ключ «только на чтение» — неизвестно.** На странице Seller API такой опции не названо
(у WB она есть и документирована — бит 30). Поэтому просьба к Ивану: при создании ключа выбрать
**минимально возможный уровень доступа** и, если в кабинете предлагается вариант только на чтение,
выбрать его. Если такого варианта нет — ничего страшного: наш транспорт всё равно не умеет писать,
а `POST /v1/roles` после подключения покажет, что ключ реально может, и панель это отобразит.

### 3.3 Тестовый контур

## 4. Фаза записи (проектируем, но НЕ строим)

Из матрицы паритета записи в маркетплейс требуют строки 5, 8, 9 и «отправка» в строках 7, 10, 11:

| функция «Комбо» | что пришлось бы вызвать | почему сейчас нельзя |
|---|---|---|
| передача остатков на площадку | WB `PUT /api/v3/stocks/{warehouseId}`; Ozon `POST /v2/products/stocks` | запись |
| передача цен | WB `POST /api/v2/upload/task` (prices); Ozon `POST /v1/product/import/prices` | запись |
| ответы на отзывы и вопросы | WB `POST /api/v1/feedbacks/answer`; Ozon `POST /v1/review/comment/create`, `POST /v1/question/answer/create` | запись |
| статусы сборки FBS, поставки | WB `POST /api/v3/supplies`, `PATCH …/supplies/*`; Ozon `/v1/posting/fbs/*` | запись |
| печать этикеток | WB `POST /api/v3/orders/stickers` | мутирующий по документации |

Как это включается потом, не ломая сегодняшний инвариант:
1. **Отдельный модуль-транспорт** `modules/marketplace/write/` со СВОИМ реестром мутаций. Реестр чтений
   и реестр записей не смешиваются никогда: в `ReadEndpoint` записать мутацию по-прежнему невозможно.
2. **Отдельный ключ** с подтверждённой областью. Ключ чтения и ключ записи — разные строки
   `tenant_integration_secret` (`provider = 'wb' | 'wb_write'`). Ключ записи отсутствует по умолчанию,
   и его отсутствие — не ошибка, а нормальное состояние.
3. **Переключатель на тенанта и на класс операций**: `mp_write_policy(tenant_id, marketplace, kind,
   enabled, enabled_by, enabled_at)`. Не один общий тумблер: «отвечать на отзывы» и «менять остатки» —
   разный риск.
4. **Обязательный dry-run**: любая операция сначала считает и показывает владельцу, что именно уедет
   (какой SKU, какое было значение, какое станет), и только подтверждение владельца отправляет.
5. **Журнал аудита** `mp_write_call` с тем же строением, что `mp_api_call`, плюс кто подтвердил.
6. **Приёмка на песочнице WB** (у Ozon её нет — значит первая живая запись делается на одном товаре и
   сразу проверяется чтением).

### Приёмка каждой задачи — на реальности
Каждая задача принимается на ЛОКАЛЬНОМ стенде (Postgres `127.0.0.1:5433`, база задачи; для
интеграционных суит `DB_HOST=localhost` — см. AGENTS.md) и цитирует в PR команды и их вывод:
счётчики строк `select count(*)`, строки `mp_sync_run`, вывод `pnpm test:unit`, скриншоты экранов.
Живой хост не трогается ни одной из задач `w11`–`w19`: выкатка — отдельная deploy-задача после
подтверждения Ивана и с `pg_dump` перед миграциями.

### Один общий запрет для всех задач
Ни одна из них не имеет права отправить в WB или Ozon запрос, которого нет в реестре чтений её
адаптера, и ни одна не имеет права добавить второе место сетевого вызова. Это проверяется не обещанием,
а суитой (раздел 2.5), и суита обязана быть зелёной в PR.
