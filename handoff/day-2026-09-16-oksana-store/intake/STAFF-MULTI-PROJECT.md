# Штаб на много проектов: один резидент, N очередей, изоляция на диске (позиция штаба, 2026-09-16 23:38 WITA; реализация — только по слову «делай»)

Вопрос Ивана 2026-09-16 23:35 WITA (дословно, ключевое): «как мне сделать так, чтобы можно было через нового оператора общаться, фиксировать задачи и передавать их в штаб не только по проекту upready-store, но и по другим проектам. К примеру у меня сейчас есть задачи для сессии в ветке research/ux-ui-patterns-specifications … я бы хотел, чтобы работа в ней запускалась через штаб проекта design-docs или возможно даже будет лучше через один общий штаб для всех проектов, который будет делать промпт для /compact после получения промпта с задачами для другого проекта … 3.1 … делать 1 штаб-сессию на каждый проект или сделать всё в одной главной штаб сессии … 3.1.1 … нужно еще хорошо обдумать как организовать хранение, структуризацию, и изоляцию контекстов проектов, чтобы в штаб-сессии оно не смешивалось».

## 1. Ответ коротко

1. **Оператор один на все проекты** (UI + скрипты из OPERATOR-SPEC.md). У записи появляется поле `project`; всё ниже по течению (индекс, документы, очередь, resume, ответы) ключуется им.
2. **Движок один (код), экземпляров N.** Очередь проекта = каталог с tasks.json/state.json/prompts/artifacts, как сегодня у дня Оксаны. Блок `project {repo, base}` в tasks.json движок уже читает (lib.mjs, `cfg.project.base`, `cfg.project.repo`) — второй проект это второй каталог, а не второй движок. Диспетчер — один процесс, обходящий реестр очередей.
3. **Штаб-резидент (Fable) один на все проекты**, но он НЕ хранилище контекстов: он судья эскалаций и приёмок. Всё состояние — на диске в каталоге очереди проекта; пакет на каждое пробуждение (сторож, escalations.log) несёт id проекта и собран только из файлов этого проекта.
4. **Почему не «штаб на проект».** После Э2 оператора Fable нужна реже 1 из 5 записей: N спящих сессий — это N процессов, N мониторов и N окон ради редких пробуждений. Одно окно дешевле, если оно не служит памятью.
5. **Почему не «/compact при каждом переключении».** Сжатие пересказывает окно, а не читает диск (правило 17a), и сводка всё равно содержит оба проекта — изоляции оно не даёт. Переключение = durable-save в каталог уходящего проекта (resume-блок, REPORT, HANDOFF status — то, что сессия делает каждый ход и так) + чтение STAFF.md приходящего. Если окно на момент переключения выше ~100k — не /compact, а /clear: свежая сессия читает только STAFF.md проекта и запись, это дешевле и чище. Порог /compact остаётся по размеру (190k), не по проекту.

## 3. Правила изоляции (что не смешивается)

1. `project` в записи — ключ всего; запись без проекта не уходит дальше карточки.
2. Корпус: индекс по корням проекта + общая память; поиск сперва внутри проекта, потом в общем; пассажи чужого проекта не выдаются.
3. Пакет любого уровня (haiku/sonnet/opus/fable) собирает скрипт только из файлов проекта записи + STAFF.md проекта.
4. Записи штаба — только в каталог очереди своего проекта. Хук 5k («сессия = свой проект») получает реестр projects.json: резидент из `~/upready/staff` пишет в зарегистрированные каталоги очередей, всё остальное блокируется как сейчас. Это правка хука по реестру, не новый хук (42e).
5. Durable-save пишет resume-блок в каталог того проекта, над которым работал ход; блок «общий штаб» — отдельно, только про реестр и резидента.
6. UI: комната на проект + общая лента. Выбор комнаты = project записи по умолчанию; haiku переопределяет только при явном упоминании проекта в тексте; сомнение → карточка «к какому проекту?» — не угадывать.
