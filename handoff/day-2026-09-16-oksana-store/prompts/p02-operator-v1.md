## Build (stage Э1 of OPERATOR-SPEC §10 — nothing from Э2/Э3)
1. **`intake/corpus.json`** — roots (the absolute paths above), excludes, `kind` per root (`report|journal|resume|memory|decision`). **`intake/index.mjs`**: incremental by mtime+size into `operator.db` (`corpus`, `corpus_fts`), one row per heading section (`#`…`###`), body ≤ 2 000 chars per row (longer sections split), masking as above; `index.mjs --stats` prints files, rows, seconds, DB bytes. A full index of the real corpus must finish under 60 s — measure.
2. **`intake/operator.db`** — tables from §3 (`prompts, records, answers, escalations, corpus, corpus_fts`), WAL mode (the UI reads while operator.mjs writes), DDL in `intake/schema.sql`, one opener module `intake/db.mjs`. The DB, `intake/answers/`, `intake/prompts/`, `intake/escalations.log` are runtime data: add them to the repo `.gitignore`.
3. **`intake/ask.mjs`** — module + CLI. `ask.mjs passages "<question>" [--n 8]` → stems → FTS (AND, then OR) → top-N `{path, heading, date, quote}` ranked by bm25 with a recency bonus (newer file mtime wins ties). `ask.mjs status` — typed from the LIVE `state.json`/`tasks.json`/`dispatcher.jsonl`: counts by status, running tasks with age in minutes, last 5 events, DONE/STOP file presence. `ask.mjs where <task-id>` — PR url and status from state, `artifacts/docs/<id>/report.md`, `D/artifacts/<id>/report.json`, frames dir, live hosts (`https://cherkashino.shipshift.dev/ru`, `https://panel-store.upready.dev`). `ask.mjs live <url>` — curl status code + time, stamped with `date`. `ask.mjs howto "<q>"` — passages from `/Users/ivanprotsko/upready/memory/` first, plus the NAMES of matching files under `/Users/ivanprotsko/upready/.private/` (names only, never content). Every command prints the answer JSON of §5 with `level:"script"` and `doc_md` assembled from the passages: for each passage a `file://` link to the path, the heading, the file date and the quote as a block quote. **Staff decision:** at Э1 the script composes the document from passages verbatim — no model prose; haiku-compose (4.1.1) is Э2.
4. **`intake/gate.mjs`** — §5 rules 1–4 as pure functions over the answer JSON + the filesystem (rule 5 «Рекомендация/Против» is Э3); CLI `gate.mjs <answer.json>` prints `GREEN` or `RED: <reasons>` and exits 0/1. Rule 3's «no paths outside sources» = every `file://` or `/Users/…` or repo-relative path in `doc_md` must be in `sources[].path` (or its parent dir).
5. **`intake/answer.schema.json`**, **`intake/records.schema.json`** (SPEC.md fields + `kind` enum `fact|where|status|live|howto|decision|bug|task|remark|order|approval`, `start_level`), **`intake/routes.mjs`** exporting `ROUTES` (kind → start level from §4) — data, not prose.
6. **`intake/parse.mjs`** — step 2: `claude -p --model haiku --output-format json --json-schema intake/records.schema.json --allowedTools ""` with `--append-system-prompt` read from `intake/parse-system.md` (Ivan's words go VERBATIM into `ivan`; one record per question/bug/task/remark; «тот вопрос про X» is resolved against the last 5 records of the thread, which the package passes in; numbered items «1. … 2. …» are separate records). Dev/test of agents = `claude -p` on the subscription (rule 25e), never the paid API. On ANY failure of `claude -p` (non-zero exit, invalid JSON, «OAuth», timeout 120 s) → exactly ONE record `kind=fact`, `title` = first sentence of the prompt, `parse:"fallback"`, the error text in `notes` — never silence (rule 20a). Store the JSON's usage into `prompts.usage`.
7. **`intake/operator.mjs`** — the resident loop (`--once` processes what is pending and exits — use it in tests). Watch `intake/prompts/*.json` (dropped by the UI or by `operator.mjs add "<text>"` for the CLI) → insert `prompts` → parse → `records` (and `intake.mjs add` for `remark|order|bug|task`, so v1 batching for the staff keeps working) → for `fact|where|status|live|howto` run the matching `ask.mjs` command → `gate.mjs` → write `intake/answers/<record-id>.md` (header: level, ts, sources with paths and file dates) → `answers` row (gate json, usage). RED gate at script level → `answers` row with `gate.ok=false` + reasons, `records.status='escalate'`, one line in `intake/escalations.log` (`ts | record_id | script → haiku | reasons`) — Э2 consumes it; the UI shows «ищет: скрипт → haiku …» with the reasons. `decision|bug|task|remark|order` at Э1: card only, `status='awaiting-ivan'`, no answer document (spec §9: tasks and bugs are prepared, never «answered»). `approval` («делай», «ок», «не то»): bind to the newest record of the thread with status `awaiting-ivan|answered`, write `verdict_ivan`; «не то» also appends an escalation line (the actual level-up is Э2).
