Три находки одной области (публичный Store API заказов), найдены приёмкой f03 при живом замере.
Источник — `handoff/day-2026-09-16-oksana-store/logs/accept-f03-guest-order-not-in-account-2.findings.md`,
раздел «Ниты», нит 1. Прочитай его целиком: там команды, заголовки и коды ответов.

## Что замерено (не повторяй веру в текст — перемерь сам, 18f)

```
curl -o /dev/null -w "%{http_code}" \
  http://localhost:9087/store/orders/order_01M2HRA9ZERJCXES657HAF7FND \
  -H "x-publishable-api-key: <pk>" -H "authorization: Bearer <токен ЧУЖОГО покупателя>"   → 200
то же БЕЗ заголовка authorization вообще                                                  → 200
```
На витрине: чужой аккаунт по прямой ссылке `/ru/account/orders/details/<id>` видит состав заказа,
адрес доставки и телефон покупателя (скриншот `artifacts/accept-f03-guest-order-not-in-account-2/06-stranger-direct-order-url-1280x900.png`).

## Что сделать

1. **`GET /store/orders/:id` требует владельца заказа.** Аноним и чужой покупатель получают 401/404
   (выбери форму и назови её в отчёте: 404 не раскрывает существование заказа, 401 честнее — реши и обоснуй).
   Гостевой заказ остаётся доступен по своему одноразовому механизму, если он есть; если его нет — скажи это прямо,
   потому что после правки страница «Спасибо» гостя не должна сломаться (проверь её тем же прогоном, задача f01).
2. **`GET /store/orders` скоуплен тенантом.** Автор f03 назвал это родственной находкой: список не ограничен
   магазином. Покупатель с аккаунтом в двух магазинах не должен видеть заказы обоих под ключом одного.
3. **Правило 20 — чинится класс, а не место.** Пройди все маршруты `/store/*`, которые отдают данные тенанта
   (`apps/backend/src/api/store/**`, плюс `middlewares.ts`), и составь таблицу: маршрут → кто может позвать
   (аноним / любой с publishable-ключом / авторизованный покупатель / владелец ресурса) → что отдаёт.
   Каждый маршрут, где «аноним» видит чужие персональные данные, — в эту же правку.
