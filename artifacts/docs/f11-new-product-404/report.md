# f11-new-product-404 — товар, созданный владелицей, открывается на витрине

Замеры: 2026-09-15, живой магазин `cherkashino.shipshift.dev` и живой движок `shipshift.dev`.
Отчёт составлен 2026-09-15 15:49 WITA.

## Что было сломано — две независимые поломки, обе подтверждены замером

**1. Панель отдавала кириллический идентификатор.** Поле «Идентификатор» в мастере создания
необязательное; пустым его оставляет любая владелица. Тогда handle делает сам Medusa 2.19, а его
`toHandle` сохраняет любые буквы `\p{L}`, кириллицу в том числе
(`node_modules/@medusajs/utils/dist/common/to-handle.js`) — «ТЕСТ QA — не покупать» стало
`/тест-qa-не-покупать`.

**2. Витрина не открывала страницу по нелатинскому идентификатору** — и открывала бы её
неправильно даже с корректным handle. Next 15.5 отдаёт динамический сегмент в том виде, в каком он
стоит в URL, то есть percent-encoded. Витрина передавала его в Store API как есть, API искал
буквальную строку `%D1%82…`, не находил и страница отвечала `notFound()`.

Вторая поломка доказана отдельно от первой: на живом движке был создан опубликованный товар с
кириллическим handle, Store API его отдавал, а витрина — нет.

```
$ curl -s -H "x-publishable-api-key: pk_8198…f1e31" --get \
    --data-urlencode 'handle=тест-f11-кириллица' --data 'fields=id,handle,title,status' \
    'https://shipshift.dev/store/products'
{"products":[{"id":"prod_01M2HZFSVY0ZRMARMEF681KFTQ","handle":"тест-f11-кириллица",
  "title":"ТЕСТ f11 кириллица — не покупать","status":"published"}],"count":1,"offset":0,"limit":50}

$ curl -s -o /dev/null -w '%{http_code}\n' -L 'https://cherkashino.shipshift.dev/ru/products/тест-f11-кириллица'
404
```

Локальная витрина этой ветки (`next dev`, тот же живой движок) с временным логом сегмента:

```
до правки:  [f11probe] params.handle = "%D1%82%D0%B5%D1%81%D1%82-f11-%D0%BA%D0%B8%D1%80%D0%B8%D0%BB%D0%BB%D0%B8%D1%86%D0%B0"   → 404
после:      [f11probe] params.handle = "%D1%82…%D0%B0" -> decoded "тест-f11-кириллица"                                          → 200
контроль:   [f11probe] params.handle = "svechi-asd-s-chesnokom-10-sht-cherkashino"                                              → 200
```

Пробный товар удалён после замера (`DELETE /tenants/products/prod_01M2HZFSVY0ZRMARMEF681KFTQ` → 200).

## Цена: поставлена ОТДЕЛЬНО, и это чужая поломка

В мастере создания поля цены в рублях нет вовсе — замер драйвера: `rubFieldCount=0` на всех трёх
товарах. Это дефект `f09`, не этой задачи. Чтобы строку приёмки «видно цену» можно было замерить,
цены выставлены после публикации через API панели
(`POST /tenants/products/:id/variants/:vid` с `prices: [{amount, currency_code: "rub"}]`, 200 на всех трёх).

## Что изменилось в коде

**Панель** (`apps/tenant-panel`)

- `src/lib/slugify.ts` — новый: транслитерация ГОСТ-образца и `toSlug`, копия импортёрской
  (`apps/backend/src/product-csv/slugify.ts`). Два приложения едут в разных образах и не делят
  пакета, поэтому копия держится тестом-близнецом (ниже).
- `routes/products/product-create/.../product-create-general-section.tsx` — идентификатор следует за
  названием, пока владелица не напишет свой; то, что она печатает в поле, транслитерируется на лету.
  Очистка поля возвращает идентификатор названию.
- `routes/products/product-create/utils.ts` — то же правило ещё раз там, где собирается запрос: для
  значения, которое форма не видела (автозаполнение браузера, вставка без `onChange`).
- `routes/products/product-edit/.../edit-product-form.tsx` — транслитерация ввода. За названием
  ничего не следует: у товара уже есть адрес, менять его молча нельзя.
- `routes/categories/category-create/...` и `category-edit/...` — то же для категорий:
  `/categories/мёд` ломается ровно так же.

**Витрина** (`apps/storefront`)

- `src/lib/util/decode-segment.ts` — новый: `decodeSegment` / `decodeSegments`. Кривая escape-
  последовательность не роняет страницу в 500, а возвращается как есть и честно даёт 404.
- Пять роутов, где сегмент URL — это ключ поиска: `products/[handle]`, `categories/[...category]`,
  `collections/[handle]`, `journal/[slug]`, `pages/[key]`. Канонические ссылки и JSON-LD по-прежнему
  строятся по сырому сегменту: там нужен URL, а не ключ.

**Бэкенд** (`apps/backend`)

- `src/product-csv/slugify.ts` — только комментарии: шапка врала про `toHandle` («strips Cyrillic
  down to nothing» — в 2.19 он её сохраняет), пример в комментарии врал про `frakciya` (таблица даёт
  `fraktsiya`). Плюс маркеры общего блока.
- `src/product-csv/__tests__/slugify-twin.unit.spec.ts` — новый: читает оба файла и сравнивает блок,
  помеченный как общий (различия в точках с запятой нормализуются — приложения форматируются
  по-разному намеренно, AGENTS.md). Плюс поведенческие проверки на названиях этого магазина.

## Чего эта задача НЕ делает

- **Не деплоит.** Правки живут в ветке; живые панель и витрина всё ещё на старом коде. Поэтому
  приёмка панели шла через локальную сборку ветки против живого движка, а поломка витрины показана
  на локальной витрине ветки. После деплоя оба конца проверяются прямо на живых адресах.
- **Не чинит уникальность идентификатора между магазинами.** `IDX_product_handle_unique` —
  общий для всей платформы, и мастер панели (в отличие от импортёра) не разруливает занятый код:
  второй магазин с товаром «Прополис» получит ошибку записи. Проверено, что три выбранных кода
  свободны, но это дыра, а не удача. Отдельная задача.
- **Не трогает уже созданные кириллические handle.** Таких в базе не осталось: единственный
  (`тест-qa-не-покупать`) был удалён приёмкой `q02`, пробный — этой задачей.
- **Не чинит цену в мастере** (`f09`).
