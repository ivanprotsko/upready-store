# Волна 2: оркестрация девяти профилей — план, построенный на ошибках пилота

Дата: 2026-09-07 · Автор: оркестратор `store-profiles` · Задача-предшественник: `t-store-profiles-pilot`
Источник чисел: журнал `~/upready/.ai/logs/orchestrator/inbox/t-store-profiles-pilot.jsonl`, отчёты агентов в `artifacts/docs/`, коммиты `f66076f 3d67e11 616b09e ee6cfff 55666fa`.

## 1. Главный вывод: в волне 2 повторяется НЕ вся программа

Стадии `S1a` (сид), `S1b` (мост темы), `S1c` (блоки витрины) — это **фундамент, он строится один раз**. Для девяти оставшихся профилей повторяется только цепочка данных:

    S2 стиль → S3 каталог → S4 рендеры → S5 сверка → S6 сборка+стенд → S7 верификация

Из этого следует главное изменение: **в волне 2 не будет параллельных зон кода в одном worktree**. Ровно этот параллелизм породил обе аварии пилота (см. §3.1). Код заморожен, агенты пишут только JSON, Markdown и байты — файлы, которые не компилируются вместе и потому не могут уронить друг друга.

## 2. Схема: роль = постоянный работник, профиль = единица очереди

Вместо «агент на стадию одного профиля» — **работник на роль, который берёт профили из очереди подряд**.

```
очередь профилей: supplements → home-goods → kids-toys → electronics →
                  womens-fashion → accessories → stationery → skincare → pet-supplies

worker-creative   : P1 → P2 → P3 → …      (style board)
worker-merch      :      P1 → P2 → P3 → … (каталог + i18n; ждёт style board СВОЕГО профиля)
worker-images     :           P1 → P2 → … (19 рендеров; ждёт каталог СВОЕГО профиля)
worker-reconcile  :                P1 → … (сверка текстов с рендерами)
worker-assembly   :                     … (theme.json, profile.json, сид, стенд)
worker-verify     :                     … (адверсарная проверка со сбросом БД)
```

Это конвейер, а не барьер: пока картинки P1 генерируются, креативный директор уже пишет style board для P3. Пропускная способность упирается в самую медленную роль, а не в сумму стадий.

### 2.1 Как работник узнаёт о следующем профиле — через ДИСК, не через сообщение

Правило 22i: сообщение живому дочернему агенту — это **форк**, а не почтовый ящик; вторая копия пишет те же файлы. Поэтому:

- очередь лежит в `artifacts/wave2/queue.json`: `[{profile, stage, state, inputs[], outputs[]}]`;
- работник в конце своей единицы работы **сам** делает `claim` следующего профиля своей роли: атомарно (запись через временный файл + `rename`) переводит запись из `ready` в `in_progress`;
- если `ready`-записей для его роли нет — работник завершается, и оркестратор поднимает нового, когда вход появится;
- оркестратор НИКОГДА не пишет живому работнику; он пишет только в очередь.

### 2.2 Планировщик вместо ручного запуска

**Прямая причина потери 25 минут в пилоте** (§4): стадия ждала не входных данных, а того, когда у оркестратора дойдут руки. В волне 2 запуск стадии определяется наличием файлов:

    scripts/wave2-scheduler.mjs — читает queue.json, для каждой роли проверяет,
    существуют ли на диске ВСЕ её inputs[]; если да и работника нет — стартует его.

Оркестратор гоняет планировщик после каждого события, а не по вдохновению.

## 3. Что сломалось в пилоте и что с этим сделано

### 3.1 Две компиляционные аварии на границе зон — потеряно ~40 минут работы двух агентов

| Что | Симптом | Почему не поймал автор |
|---|---|---|
| `globals.css` импортировал `themes.css` НИЖЕ tailwind-импортов, которые инлайнятся | Turbopack отверг импорт, **все** маршруты 500 | Файл писал S1b, убивался об него S1c |
| `image-frame.module.css` нёс 11 правил `:global(...)` верхнего уровня | css-loader в PURE-режиме — ошибка компиляции, `next build` красный | Файл писал S1c, убивался об него S1b |

**Меры волны 2:** (а) параллельных зон кода нет вовсе — класс исчезает; (б) если код всё же правится, оркестратор держит `build-heartbeat.mjs`, который раз в N минут гоняет `next build` в СВОЕЙ dist-директории и пишет `artifacts/wave2/build-status.json`; работник, увидевший `red`, не чинит чужое, а переключается на работу, не требующую страницы.

### 3.2 Сгенерированные файлы чуть не попали в историю

`next-env.d.ts` и `tsconfig.json` Next переписывает под активный `NEXT_DIST_DIR`. Коммит прибил бы репозиторий к сборочной папке одного агента.
**Мера:** список never-commit в `artifacts/wave2/never-commit.txt`, и оркестратор прогоняет `git checkout HEAD -- <список>` перед каждым коммитом.

### 3.3 Незакрытый `pkill -f 'medusa develop'` снёс стенды

Стенды `:9023` и `:8033` умерли посреди прогона.
**Мера:** запрет `pkill -f` в промптах; работник обязан записывать PID в `artifacts/wave2/pids.json` и убивать только по PID.

### 3.4 Шаблон промпта был зашит под одну товарную форму — цена 3 из 19 оплаченных кадров

`style-board §5.4` содержал `A single right shoe, alone in frame` и по замыслу подставлялся «verbatim, unchanged, for every product». Для трёх аксессуаров это ложь, а перегенераций нет.
**Мера, обязательная для каждого профиля:** style board отдаёт шаблон **на семейство товаров**, а не один на всех; оркестратор перед первым платным рендером **прогоняет модуль промптов** и проверяет, что для каждого семейства строка своя (в пилоте это поймал прогон: `stillLifeBody` не содержит фразу про туфлю, `packshotBody` содержит).

### 3.5 Провайдер не отдаёт цену предсказания

Замерено: `costUsd: null`, `costSource: "not-exposed-by-provider"`, `costFieldsFound: 0` у `nano-banana-2`.
**Мера:** снимать баланс аккаунта Replicate ДО и ПОСЛЕ батча каждого профиля и записывать разницу; предсказывать цену запрещено.

### 3.6 Базу для пиксельного сравнения нельзя было восстановить

T0h.5 требовал скриншоты «до любых изменений», но в то окно все страницы отдавали 500.
**Мера:** любые baseline-скриншоты снимаются **первым действием прогона**, до старта любого работника.

### 3.7 Отчёт агента может не дойти

Финальный конверт S1a до оркестратора не дошёл; работа была цела только потому, что лежала на диске.
**Мера:** контракт — **отчёт на диске**; оркестратор считает стадию закрытой по наличию файла и его содержимому, а не по полученному сообщению.

### 3.8 Окно оркестратора вышло за лимит (371k при 250k)

**Мера:** оркестратор не читает отчёты агентов в своё окно. Гейт каждой стадии — скрипт `scripts/gate.mjs <stage> <profile>`, который сам читает отчёт и возвращает `{ok, counts}` в одну строку.

## 4. Почему генератор изображений стартовал поздно

Вход S4 — `imageBrief` каждого товара, а он рождается в S3; S3 в свою очередь ждёт раздел бренда из S2. Фактические времена: S2 закрыт **20:42**, S3 закрыт **21:06**, S4 запущен **21:31**.

То есть **самое раннее, когда S4 мог стартовать по зависимостям, — 21:06**, а стартовал он в 21:31. **Потеряно 25 минут, и это ошибка оркестратора, а не свойство конвейера:** в этот момент оркестратор закрывал гейт S1 и чинил две аварии из §3.1. Зависимость тут ни при чём.

Ещё раньше 21:06 S4 стартовать не мог: без брифов рендерить нечего. Но цепочку можно укоротить — см. §5.

## 5. Что даст ускорение в волне 2

1. **Планировщик по входам (§2.2)** — снимает те самые 25 минут и все будущие такие же.
2. **Ранний стенд темы без картинок.** Проверено в пилоте прямо сейчас: `theme.json` и `profile.json` выводятся из style board и каталога и **не зависят от рендеров**. Значит стадия «тема + стенд» может идти ПАРАЛЛЕЛЬНО с генерацией, а не после неё. Иван видит палитру, типографику и раскладку, пока картинки ещё считаются.
3. **Гейт первого кадра отдельно от батча.** Один рендер первого товара запускается сразу, как только у S3 готов ПЕРВЫЙ товар, а не весь каталог: стилевой риск снимается на 15–20 минут раньше.
4. **Фундамент не повторяется** — из ~1 часа 20 минут пилота на девять профилей не переносится ничего из S1a/S1b/S1c.

## 6. Оценка волны 2

Критический путь одного профиля по замерам пилота: S2 ≈16 мин + S3 ≈24 мин + S4 ≈15 мин генерации + S5/S6/S7 (в пилоте ещё не замерены). При конвейере из шести работников девять профилей упираются в самую медленную роль, а не в сумму: ожидаемо **не 9 × полный цикл, а ≈ полный цикл + 8 × такт самой медленной роли**. Точный такт станет известен после S5–S7 пилота — до тех пор любая цифра была бы выдумкой.
