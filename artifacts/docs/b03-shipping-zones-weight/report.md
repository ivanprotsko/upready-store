# b03-shipping-zones-weight — региональные зоны РФ и «цена за кг по зонам»

Отчёт составлен 2026-09-15 22:27 WITA. Ветка `feat/day16-shipping-zones-weight`, база `dev`
(`origin/dev` = `1088507f` влита в ветку). Диф к базе: 61 файл, +1859 / −50.

Задача из `artifacts/q03-gap-recheck/gap-recheck.md`, «Осталось критичного», пункт 4: живьём было два
способа доставки с фиксированной ценой, заготовка тарифа по весу и одна зона «Все страны магазина».
Оксана просила расчёт «цена за кг по зонам» (обращение #463839).

## Что сделано

### 1. Девять готовых зон по России, с редактированием
`apps/backend/src/shipping-tariffs/ru-zone-presets.ts` — Москва и область, Санкт-Петербург и область,
Центр, Северо-Запад, Юг, Поволжье, Урал, Сибирь, Дальний Восток. Зона — это НАЗВАНИЕ плюс список
кодов регионов из существующего `ru-regions.ts`; строками в БД зоны не становятся. Девятка покрывает
все 85 субъектов ровно по одному разу — это проверяет юнит-тест, а не комментарий.

`GET|POST /tenants/shipping-methods/zone-presets`: чтение списка зон и служб; запись создаёт ПО ОДНОМУ
обычному способу доставки на каждую отмеченную зону. Дальше это обычные способы: та же форма
редактирования, то же удаление, список регионов открыт для правки. Повторный вызов ничего не
дублирует — способ с таким именем пропускается.

Экран в панели: `/shipping` → кнопка «Зоны по России» (`shipping-zones.tsx`). Таблица из девяти строк:
галочка, название зоны с числом регионов, базовая ставка, цена за килограмм; сверху выбор службы и
минимальный вес; уже созданные зоны показаны выключенными строками «Такой способ уже создан».
В форме одного способа (`shipping-method-form.tsx`) появился быстрый выбор: кнопка «Урал» проставляет
6 галочек регионов, после чего список правится вручную — это и есть «создаёт зоны из регионов
с редактированием».

### 2. Правило «базовая цена + цена за кг» по зоне
Сам тариф `per_kg` существовал с t04; новым стало то, что цена задаётся ПО ЗОНАМ (таблица из девяти
цен за один сохранение) и что зона теперь имеет ИМЯ: бэкенд пишет `data.zone.label` при каждом
сохранении (`labelledZone` в `helpers.ts`), и это имя видят и владелица, и покупатель, и заказ.

### 3. Вес из карточек товаров + импорт из метаданных
`apps/backend/src/scripts/import-product-weights.ts` + чистый разбор
`shipping-tariffs/weight-from-metadata.ts`. Источники по порядку: характеристики каталога
(«Вес товара, г»: 30, «Вес (с упаковкой)»: «70 г», «0,15 кг»), затем простой ключ
`metadata.weight`/`weight_g`/`вес`, затем — только по `FROM_TITLE=1` — название товара и варианта
(«Сеннол 125 гр»). Число без единицы измерения не угадывается: 30 кг и 30 г одинаково правдоподобны,
и неверное молча завышает доставку каждому покупателю. Сухой прогон по умолчанию, запись по `APPLY=1`,
повторный прогон ничего не переписывает.

### 4. Реальная служба как способ
`shipping-tariffs/carriers.ts`: СДЭК, Почта России, свой курьер, самовывоз. Имя способа честное —
«СДЭК (расчёт по тарифу магазина)», потому что цену считает магазин по своему тарифу, а не калькулятор
СДЭК. У каждой службы есть инструкция владелице, она показана прямо на экране зон («Что делаете
вручную»). Поле трек-номера уже было (форма «Создать отгрузку» в заказе, принята в t04); новое —
что заказ теперь ЗАПОМИНАЕТ зону и службу: `validateFulfillmentData` тарифного провайдера кладёт
`zone_label` и `carrier` в данные способа доставки заказа.

### Вес товаров Оксаны
До импорта: вес был у 5 вариантов из 38 (и ни у одного товара). После двух прогонов скрипта —
`TENANT=cherkashino APPLY=1` и `TENANT=cherkashino APPLY=1 FROM_TITLE=1`:

```
[cherkashino] товаров 38: вес уже задан у 0, найден в метаданных у 12, не найден у 26
[cherkashino] записан вес у 12 товаров.
[cherkashino] товаров 38: вес уже задан у 12, …, из названий вариантов 8
[cherkashino] записан вес: товаров 0, вариантов 8.
[cherkashino] товаров 38: …, из названий вариантов 0     ← повторный прогон, идемпотентно
```

Итого 23 варианта из 38 несут собственный вес (замер в БД стенда). Остальные 15 карточек веса не
имеют нигде — ни в характеристиках, ни в названии; для них работает «вес по умолчанию» со страницы
«Доставка» (500 г), и это видно покупателю по строке расчёта. Список этих 15 печатает сам скрипт
строками «БЕЗ ВЕСА: …» — владелице проще проставить вес по списку, чем искать.

## Чего НЕ сделано и почему

1. **Трек-номер end-to-end в этом PR не перемерен.** Форма отгрузки с трек-номером — код t04, диф её
   не трогает; она принята живьём в приёмке t04 (заказ №6, панель и кабинет покупателя показывают
   «СДЭК 80112233445566»). Новое здесь — только честное имя службы и инструкция владелице, они
   измерены на скриншотах выше.
2. **API-интеграции со СДЭК нет** — она и не просилась: цену считает тариф магазина, накладная
   создаётся в кабинете СДЭК руками. Так написано и в имени способа, и в блоке «Что делаете вручную».
3. **Зоны заданы только для России.** `REGIONS_BY_COUNTRY` знает регионы одной страны; для Беларуси
   или Казахстана зона задаётся «страна целиком». Это ограничение t04, не новое.
4. **Мультивалютность зон.** Цена за килограмм пишется в валюте магазина (`rub`); магазин с двумя
   валютами задать разные цены по валютам не может — тот же нит, что записан в приёмке t04.
5. **Деплоя не было** (правило 21c): всё измерено на локальном стенде с клоном базы клиента.
