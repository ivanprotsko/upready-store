## Design decisions taken (grounded, not asked — rule 18d/27d)

| Decision | Why, with evidence |
|---|---|
| Pickup point identity lives in `cart.metadata` (`pickup_point_id/name/address/hours`), not `shipping_address` | `checkout-shipping-section/index.tsx:204-221` already blanks `shipping_address` on pickup; `checkout-info-rows/index.tsx:32,47-53` already reads structured data from `cart.metadata` for contacts — overloading the address the app deliberately empties would fight `addressNotNeededForPickup` |
| Pickup search is a client-side substring filter over an already-fetched list | map §2: "N stock locations … per profile city" is a handful of points, not a paginated catalog — no new API surface needed |
| Failure page = the existing `/cart?error=…` redirect target, read by `CartTemplate`, per the map's own recommendation | map §9 fork 1, §3.3 already traced every redirect site to `/cart`; a second route would duplicate what's wired and contradict that evidence |
| Two documented demo-card numbers exercise two different gaps: `…0000` declines **inline** (item 2), `…9999` **redirects** to `/cart?error=order_failed` (item 4) | map §5 recommends rejecting a documented number before `placeOrder()`; §3.3 traces `payment_failed` vs a cart that "didn't convert" as two distinct causes — one honest mechanism makes both reachable by a real click on every stand with no Stripe keys anywhere |

## Acceptance (rule 27d)

The six base criteria, adapted to these screens:

1. No identifier reaches the screen — a visitor reads "Kerbstone Kreuzberg" and "Mon–Sun 11:00–21:00", never a `stock_location_id` or a raw `error=order_failed`; frame 10's sentence never repeats the query-string value.
2. No name or address truncates with an ellipsis at 390 px — frame 5's rows and frame 9's mobile shipping block wrap onto a second line instead (shown, not merely stated).
3. The pickup list never exceeds one screen without the search field — frame 2 fits four rows at 1440 with no scroll; frame 5 states explicitly that a fifth+ row scrolls, search present from the first frame.
4. Every status is a dot + sentence — frame 7's "declined" and frame 10's failure banner both draw the `StatusBadge` dot shape already in this codebase, never a bare enum like `order_failed`.
5. Hierarchy (section/row/meta) is visually distinct — frame 4 keeps "Shipping method" as the section, the pickup point as the row, hours/phone as meta in a lighter weight, matching the existing `h2-docs`/`txt-small`/`text-ui-fg-subtle` split already used on that screen (`checkout-info-rows/index.tsx:80-92`).
6. Every frame above is drawn as an ASCII box, not described in prose.

Two criteria specific to this document:

7. The failure page (frame 10) is reachable from a real click on a live stand with no payment keys configured — the `9999` demo card (frame 7) is the trigger, and its route matches the one `payment-return/route.ts` already uses, so the same component demonstrates both today's demo path and tomorrow's real Stripe path.
8. A visitor can always tell why a pickup point row differs from another — name, address and hours are three separately-styled lines per row (frames 2, 3, 5), never one comma-joined string that would make "Mon–Sat 10:00–20:00" read as part of the street address.
