## T0h. Theme presets (you or one Opus agent, ≤100k; the two preset files may be two Sonnet agents in parallel)

1. **Dictionary and token map values.** `specs/design-system/token-map.json` gains, per row, `canonToken` (a name from `geist-kit/theme.css`) and `bridge` (the CSS declaration that makes the Medusa variable follow the canon token, e.g. `--fg-base: var(--foreground)`). Cover **all 88** preset variables, not only the 26 in markup: `status` is `mapped` (one canon token), `diverged` (needs a derived value, say how: `color-mix`, alpha) or `open` (no canon counterpart yet; list them for the architect). Print the counts.
2. **Preset files** `specs/design-system/themes/medusa.theme.json` and `geist.theme.json` per `specs/design-system/theme-preset.schema.json` (`upready.theme-preset/v0`). `medusa`: values read by a script from the preset's `dist/index.js` `:root`/`.dark` blocks and translated through the token map, `source` names file and version. `geist`: values of `geist-kit/theme.css` at its current commit; the vendor copy follows geist-kit's "Consumption & drift" rule (`source: geist-kit@<commit>` + an entry in `~/upready/packages/reuse-index.json` in the same commit). Both presets carry the **same key set** in both modes; the build script fails on a difference and prints `N keys, 0 missing`.
3. **Build script** `apps/storefront/scripts/build-themes.mjs` (`pnpm --filter @dtc/gorgo-medusa-storefront themes:build`): validates both files with Ajv, emits `apps/storefront/src/styles/themes.css` with `[data-theme="<id>"][data-mode="<mode>"] { --background: …; }` blocks plus one `:root` bridge block from the token map, imported from `globals.css`. Keep the existing `--fg-interactive` override working: it becomes a `diverged` row, not a special case. Never edit anything under `node_modules`.
4. **Attributes and pre-paint.** `<html data-theme="medusa" data-mode="light">` by default; an inline pre-paint script in `<head>` (pattern: `~/upready/projects/chrxnasdmds/apps/storefront/src/lib/theme/pre-paint.ts` + `storage-keys.ts`, allow-list of ids, idempotent, never throws) reads `localStorage` and sets both attributes before hydration. One module `apps/storefront/src/lib/theme/` owns storage keys, attribute names, `apply*()` and `readInitial()`.
5. **Compatibility test (this is the proof Ivan asked for).** Playwright in Docker on `:8001`: screenshots of four pages (home, a category listing, one PDP, the cart) at 1280×800 **before** any change of this step (take them first, commit them as the baseline), then **after** with `medusa`/`light` active: pixel difference ≤ 0.1 % per page, numbers copied. Then `geist` in both modes on the same four pages: zero elements whose colour still comes from an `open` bridge row (the script lists `open` rows; the test asserts each page's computed colours never equal the Medusa fallback of an `open` variable). Also assert `getComputedStyle(document.documentElement).getPropertyValue('--background')` changes when `data-theme` flips, and that `body` background follows.

## T0i. Hidden settings panel (design stage first, then you or one Opus agent, ≤100k)

**Design stage (rule 27d, mandatory before code).** Canon: `~/upready/packages/geist-kit/AGENTS.md` (sentence case, weight ≤ 600, one accent, Geist Mono `tabular-nums` for numbers, hairline borders, status = 8 px dot + text). Write `artifacts/docs/2026-09-06-theme-panel-mockup.md`: an ASCII mock-up of the floating button and the popover **that shows the behaviour** — hold → password dialog → button appears → popover → preset flip → mode flip → reload without a flash — one frame per state, in the style of `~/upready/projects/design-docs/docs/theme-configurator/06-ui-panel.md`. Examples to read, in this order: `~/upready/projects/chrxnasdmds/apps/storefront/src/modules/layout/components/side-menu/theme-panel.tsx` (sections, segment buttons, `apply*` → `<html data-*>` + localStorage), `~/upready/projects/grmlnk/prototype/src/engine/color/presets.ts` (presets as word → number dictionaries), `06-ui-panel.md` (layout, eye criteria). Do not copy their palettes; copy the mechanics.

**Flow, as Ivan described it.**

1. **Long press 2 s on the brand element**: desktop `nav-store-link` in `modules/layout/templates/nav/index.tsx`, mobile the `/` link in `modules/layout/components/bottom-nav/index.tsx`, checkout the brand in `app/[locale]/(checkout)/layout.tsx`. Pointer events (touch and mouse both); a press shorter than 2 s stays an ordinary navigation to `/`; movement over 10 px cancels; no visible affordance for visitors.
2. **Password dialog** (native `<dialog>` or the storefront's existing modal primitive, your call in one sentence): one field, one button, an error line. `POST /api/devtools/unlock` compares against `STOREFRONT_DEVTOOLS_PASSWORD` (server-only env, documented in `apps/storefront/README.md` with the other variables; empty variable = feature disabled, route answers 404). Success sets an httpOnly, `SameSite=Lax`, signed cookie for 7 days. The password never enters the client bundle (rule 41: guardrails are code).
3. **Floating button** bottom-left, small (≈40 px), only rendered when the cookie is present (server component reads `cookies()`; the HTML of a visitor without the cookie contains neither button nor popover). A "lock" action removes the cookie.
4. **Popover with settings**: preset (`medusa` / `geist`, labels from the preset files, never raw ids on screen), mode (`light` / `dark`), "Reset to default", and one source line "rendered from N tokens of preset <label>" (rule 18e; N from the build output). Selection applies instantly through the `apply*()` module and persists per browser. Fonts and radius are **not** in scope today (rule 32a); leave the section layout able to take them.
5. **Styling**: the panel wears the Geist canon on the 19 tokens of `geist-kit/tokens.css`, scoped under the panel root, independent of the storefront's active preset (same decision as the configurator's D2: the tool is dressed in the canon, not in the shop's theme). Later the configurator's own `panel/` (its M4) replaces the inside of this popover; keep the mount point one component.

**Tests (Playwright in Docker, `tests/ui-lab` or `tests/devtools`, your call):** hold 1.5 s → URL is `/`; hold 2 s → dialog visible; wrong password → error text visible, no cookie; right password → cookie set, button visible; flip preset → `--background` on `<html>` and `body` background change; reload → `data-theme` is already set before the first paint (observe with `page.addInitScript` a `MutationObserver`/first-read on `documentElement` and assert the attribute is present at `DOMContentLoaded`); `curl` of `/` without the cookie contains no `data-testid="devtools-button"`. Every check with its reverse run (remove the behaviour → red), counts copied into the report.
