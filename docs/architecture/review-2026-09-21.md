## How To Read A Finding

Each finding carries the same five fields.

- Evidence: `path:line` in this repository, opened during the review.
- Risk: one sentence, from the point of view of a shop that takes real money.
- Recommendation: what to change.
- Estimate: working time for one engineer who knows the codebase.
- Class: `do now in this unit`, `separate task`, or `needs Ivan's decision`.

Findings are ranked inside a chapter by risk. The cross-chapter ranking is the table in
Ranked Risks, which is rebuilt whenever a chapter lands.

### What Holds

The `/tenants/*` namespace derives the tenant from the authenticated actor and from nothing else.
`getTenantScope` reads `tenant_admin` by `req.auth_context.actor_id`
(`apps/backend/src/api/tenants/tenant-scope.ts:38-63`). Every per-area helper opened so far calls
it instead of reading a tenant id from the request: `products/csv-context.ts:136`,
`marketplace-orders/load-feed.ts:105`, `marketplace-analytics/load-analytics.ts:175`,
`marketplaces/draft-handlers.ts:40`, `notification-settings/helpers.ts:89`,
`requisites/helpers.ts:148`, `marketplace-keys.ts:170,275,320`. A foreign id answers `404`, never
`403`, so a response does not confirm that another shop's row exists (`tenant-scope.ts:17-19`,
`orders/helpers.ts:18-31`).

The routes that move money assert ownership before their workflow runs. All nine
`orders/[id]/**` routes call `assertOwnedOrder`, `payments/[id]/capture` calls
`assertOwnedPayment` (`orders/helpers.ts:22-75`), and the inventory batch route calls
`assertOwnedInventoryItems` (`products/helpers.ts:148`).

Store order reads are scoped to the shop of the publishable key and to the owner or the holder of
the guest token (`apps/backend/src/api/store/order-access.ts:95-132`, wired at
`api/middlewares.ts:1452,1458,1463,1472`). The integration spec covers the cross-shop case
(`apps/backend/integration-tests/http/store-order-isolation.spec.ts:201-206`).

The `/store/tenant/*` routes take the shop from the sales channel of the publishable key and
answer `404` for a key with no tenant behind it, so they fail closed
(`apps/backend/src/api/store/tenant/resolve-tenant.ts:17-32`). The guest order claim refuses a key
with no channel the same way (`api/store/customers/me/claim-orders/route.ts:37-48`), which is the
behaviour T-2 asks of the order reads.

The six ownership helpers an earlier pass had matched by name only were opened, and each takes its
scope from the actor. `getTenantWarehouse` and `assertOwnedPaymentSettings` call `getTenantScope`
(`shipping-methods/helpers.ts:54-55`, `payment-settings/helpers.ts:80-84`). `listTenantMethods` and
`assertOwnedMethod` filter by the service zones of that warehouse (`shipping-methods/helpers.ts:255-285`).
`getTenantCustomerAggregates` starts from `listTenantOrderIds` (`customers/helpers.ts:72-75`).
`getTenantWithDomains` reads `tenant_admin` by `req.auth_context.actor_id` itself
(`domains/helpers.ts:25-45`), the one copy of that read outside `getTenantScope`.

The platform routes under `/admin/tenants` carry only validators in `api/middlewares.ts:1296-1331`
and rely on the framework's default `/admin/*` authentication for the actor type `user`, so a
`tenant_admin` token does not open them. `GET /storefront/by-host` is public by design and answers
the publishable key, which every storefront page already sends (`api/storefront/by-host/route.ts:19-22,150-170`).
Uploads from the panel are stored under `tenants/<tenant id>/` taken from the actor, not from the
request (`api/tenants/uploads/route.ts:38-44`).

### T-1. The Tenant Order Link Has One Chance To Be Written

- Evidence: `apps/backend/src/subscribers/order-placed-tenant-link.ts:18-20` runs the link
  workflow with no `try`, no retry and no dead-letter record.
  `apps/backend/src/workflows/tenant/link-order-to-tenant/index.ts:21-37` reads the order with
  `throwIfKeyNotFound: true`, so a read that races the order commit throws. No file under
  `apps/backend/src/scripts`, `apps/backend/src/jobs` or `apps/backend/docker-entrypoint.sh`
  mentions the link or the workflow, so nothing converges a missed link. The panel lists orders
  only through that link (`tenant-scope.ts:95-113`). Redis backs the event bus only when
  `REDIS_URL` is set and the process is in production or `USE_REDIS=true`
  (`apps/backend/medusa-config.ts:10,38,42`). Otherwise the bus is in memory and an event that
  was being handled when the process restarted is gone.
- Risk: a customer pays, the handler fails once, and the order never appears in the owner's
  panel, so it is never packed or shipped.
- Recommendation: add an idempotent convergence script `link-orphan-orders` under
  `src/scripts`, wired into `docker-entrypoint.sh` and into a scheduled job, that links every
  order whose sales channel belongs to a tenant and that has no `tenant_order` row. Log a missed
  link at `error` level in the subscriber.
- Estimate: 4 hours with an integration spec.
- Class: separate task. It adds behaviour, so it is not a refactor.

### T-6. A Caller Chooses The Fields, And The Tenant Link Is Not On Any Block List

Found by reading. Not measured yet. The two-shop stand built for acceptance line 4 will carry the
three requests named under Recommendation, and this finding is rewritten with the answers.

- Evidence: 40 route files under `apps/backend/src/api/tenants` hand `req.queryConfig.fields` to
  the query, and their middleware entries borrow the Admin query configs, for example
  `api/middlewares.ts:701-705` for `apps/backend/src/api/tenants/orders/[id]/route.ts:16-20`. Of the
  18 Admin query configs checked, only `customers`, `promotions` and `product-categories` carry an
  `allowed` list (`@medusajs/medusa/dist/api/admin/*/query-config.js`). `orders`, `payments`,
  `products`, `campaigns`, `sales-channels`, `stock-locations`, `stores`, `inventory-items`,
  `reservations`, `returns`, `claims`, `exchanges`, `collections`, `shipping-options` and `regions`
  carry none, and no entry under `/tenants` adds one. The ownership check covers the id in the
  path. It does not cover a relation asked for through `?fields=`. If the order to customer link
  resolves in both directions, `fields=*customer.orders` on the shop's own order names the orders
  the same buyer placed in every other shop. Medusa 2.19 knows this class of request and strips `orders`, `carts`,
  `customer` and the payment relations on the public Store API
  (`@medusajs/medusa/dist/api/store/utils/disallowed-fields.js`), and the framework sets restricted
  fields only for `/store` and `/admin` (`@medusajs/framework/dist/http/router.js:232-241`), so
  `/tenants` gets neither list. The Store API list knows nothing of this repository's own links
  either: `apps/backend/src/links/tenant-product.ts` makes `tenant` a relation of every product,
  and the tenant model hangs `admins`, `requisites`, `notification_settings`, `domains` and
  `integration_secrets` off it (`apps/backend/src/modules/tenant/models/tenant.ts:36-93`). The
  secret payloads are AES-256-GCM ciphertext (`models/tenant-integration-secret.ts:62`), so a read
  would not hand over a usable key.
- Risk: a shop owner reads what a buyer ordered in other shops, and an anonymous visitor holding
  the public key reads the owner's e-mail, legal requisites and notification addresses of a shop.
- Recommendation: measure first. (1) `GET /store/products?limit=1&fields=id,*tenant,*tenant.admins,*tenant.requisites`
  with a shop key and no login. (2) `GET /tenants/orders/<own id>?fields=id,*customer.orders` as
  the owner of shop A, for a buyer who also ordered in shop B. (3) `GET /tenants/products/<own id>?fields=id,*sales_channels.tenant.admins`.
  If any of them answers with data, give every `/tenants` entry a `disallowed` list
  (`tenant`, `orders`, `carts`, `customer.orders`) through one shared wrapper around
  `validateAndTransformQuery`, and add `tenant` to the Store API through
  `projectConfig.http.restrictedFields.store`.
- Estimate: 1 hour to measure. 6 hours for the wrapper, the config line and seam specs.
- Class: separate task. It narrows answers, so it is not a refactor.

### T-7. A Customer Row Belongs To The Platform, And A Shop Reads All Of It

- Evidence: `apps/backend/src/api/tenants/customers/[id]/route.ts:11-13` states that a customer is

  buyer account should be one per platform or one per shop is a product decision, listed under
  Decisions For Ivan.
- Estimate: 2 hours for the narrowing with a seam spec.
- Class: needs Ivan's decision for the account model. The narrowing is a separate task.

### How The Cache Is Keyed And Cleared

A cached read is a `fetch` with `cache: "force-cache"` and no `revalidate` period, so an entry
lives until something clears it. The catalog tags are built per visitor and per shop:
`getCacheOptions` answers `<tag>-<_medusa_cache_id>-<handle>`
(`apps/storefront/src/lib/data/cookies.ts:169-190`). The webhook cannot know a visitor's cache id,
so `revalidateTag("products")` in the route matches only the three reads that use the bare tag,
the sitemap and `llms.txt` (`apps/storefront/src/app/sitemap.ts:71,103,136`,
`app/llms.txt/route.ts:69,81,96`). Catalog pages are cleared by `revalidatePath`, and a path is
one path for every shop on the process (`app/api/revalidate/route.ts:10-21`). The tenant document
tags (`tenant-home-<handle>`, `tenant-pages`, `tenant-articles`, `product-attributes`,
`product-reviews`) carry no visitor id and are cleared by tag.

### C-1. No Inventory Event Reached The Storefront. Fixed In This Unit

- Evidence: the product list asks for `+variants.inventory_quantity` under `cache: "force-cache"`
  (`apps/storefront/src/lib/data/products.ts:77-84`). On base `b7e05c8b` the revalidation
  subscriber listed no inventory or reservation event
  (`apps/backend/src/subscribers/product-updated.ts:15-40`), and the webhook route had no branch
  for them.
- Risk: a product shows as in stock after the last unit was sold, and the shop takes money for
  goods it does not have.
- What changed: commit `2cb4e519` adds `apps/backend/src/subscribers/inventory-updated.ts`, which
  forwards Medusa's six workflow events `inventory-level.*` and `reservation-item.*`, and a branch
  in the route that clears the five pages that show stock. The workflow events were chosen over
  the module events `inventory.inventory-level.*` because every Admin path that edits a level
  emits them, `completeCartWorkflow` emits `reservation-item.created`, and the Medusa linter asks
  for them. Specs: `storefront-revalidate/__tests__/inventory-subscriber.unit.spec.ts`,
  `app/api/revalidate/route.test.ts`.
- Class: do now in this unit (recorded defect `t-port-stale-inventory-fix`). Done. Its cost is
  finding C-4.

### C-3. A Lost Webhook Leaves A Page Stale With No Upper Bound

- Evidence: `notifyStorefrontRevalidate` makes one attempt, logs a failure and returns
  (`apps/backend/src/storefront-revalidate/index.ts:44-68`). It skips the call when neither address
  variable is set (`:35-40`). No catalog read sets a `revalidate` period, so nothing else ever
  refreshes the entry. The subscribers run on the event bus, which is in memory unless Redis is
  configured (finding T-1), so a restart during a burst of edits loses the events as well.
- Risk: one storefront restart or deploy that overlaps an edit in the Admin leaves a wrong price
  or a sold-out product on sale until someone edits the same product again.
- Recommendation: give the catalog reads a ceiling, `next: { revalidate: 3600 }` next to the tags,
  so the worst case is one hour and not forever. Retry the webhook twice with a short delay.
- Estimate: 2 hours with tests.
- Class: separate task. A ceiling changes when pages re-render, so it is not a refactor.

### C-4. One Shop's Edit Clears The Catalog Pages Of Every Shop, And Now Every Order Does Too

- Evidence: catalog pages are cleared by path, and the route states that a path is shared by every
  shop on the process (`apps/storefront/src/app/api/revalidate/route.ts:13-21`). The per visitor
  suffix is what forces the path (`lib/data/cookies.ts:169-190`). Since commit `2cb4e519` a
  reservation clears the product, store, category, collection and home paths, and every placed
  order makes a reservation (`route.ts:74-94`).
- Risk: none for correctness. With twenty shops taking orders, the rendered catalog pages of all
  twenty are dropped on each order, and the cache stops paying for itself exactly when traffic is
  high.
- Recommendation: tag catalog reads by shop and not by visitor (`products-<handle>`), let the
  subscriber resolve the shop of the product or of the inventory item and send `handle`, and clear
  by tag. The visitor id stays only on reads that are per visitor.
- Estimate: 1 day, with a load measurement before and after on the stand.
- Class: separate task.

### C-5. Delivery Options Are Cached Per Cart And No Panel Edit Clears Them

- Evidence: the options of a cart are read under `force-cache` (`apps/storefront/src/lib/data/fulfillment.ts:13-46`,
  `:172-182`, `lib/data/cart.ts:601-610`). No route under `apps/backend/src/api/tenants/shipping-methods`
  or `tenants/delivery-settings` calls `notifyStorefrontRevalidate`, and the webhook route has no
  delivery branch. The entry is cleared only by the same visitor's cart actions, through the
  `fulfillment` tag (`lib/data/cart.ts`, `updateCart`).
- Risk: an owner raises a delivery price or turns a method off, and a buyer with an open cart
  still sees the old list. The backend computes the amount on its side, so the buyer may see one
  price in the list and another in the total. Read, not measured.
- Recommendation: read delivery options with `no-store`, the way the cart itself already is

## Chapter 4. Storefront Data Layer And Middleware

Status: READ for `apps/storefront/src/middleware.ts`, `lib/tenant/resolve.ts`,
`lib/tenant/redirects.ts`, `lib/data/cart.ts`, `lib/data/locale-actions.ts`, `lib/data/cookies.ts`
and the cache options of every file under `lib/data` (chapter 2). The other data files were read
only where a finding cites them.

### What Holds

The middleware asks the backend for the shop of a host and for its redirect table at most once a
minute per process, not once per request (`apps/storefront/src/lib/tenant/resolve.ts:68-96`,
`lib/tenant/redirects.ts:12-68`), and a backend error keeps the previous answer for the shop
instead of caching «no shop here» (`resolve.ts:110-119`). The pure parts of the middleware have
unit tests of their own (`lib/tenant/request-shop.test.ts`, `lib/tenant/origin.test.ts`,
`lib/geolocation/resolve-country.test.ts`). The cart and the orders are read with `no-store`, with
the measured reason written next to the code (`lib/data/cart.ts:52-75`). `lib/data/cookies.ts` is
`server-only`, so no cookie helper can become a Server Action by accident.

### D-1. Every Customer Read Pulls Every Order Of The Buyer, And Nothing Reads Them

- Evidence: `retrieveCustomer` asks for `fields: "*orders"` under `force-cache`
  (`apps/storefront/src/lib/data/customer.ts:33-44`), and eight call sites use it. A search of
  `apps/storefront/src` finds no read of `customer.orders`. The account pages list orders through
  `listOrders()` (`app/[locale]/(main)/account/@dashboard/page.tsx:26`), which the backend scopes to
  the shop (`apps/backend/src/api/store/order-access.ts:169-186`). `GET /store/customers/me` has no
  such scope: Medusa allows `orders` there
  (`@medusajs/medusa/dist/api/store/customers/query-config.js:18-23`) and no entry in
  `apps/backend/src/api/middlewares.ts` covers the route, so the answer carries the buyer's orders
  from every shop on the platform.
- Risk: each page of a signed-in buyer moves their whole order history across the wire and into
  the data cache of a shop that has no business holding another shop's orders.
- Recommendation: drop the `fields` line. On the backend, add `orders` to the fields refused on
  `/store/customers/me`, which belongs with finding T-6.
- Estimate: 30 minutes for the storefront line with a test, after a check that the default fields
  stay the same without it.
- Class: do now in this unit for the storefront line. The backend half is a separate task.

### D-2. The Shop Lookup Cache Grows With Every Host Name A Client Sends

- Evidence: `apps/storefront/src/lib/tenant/resolve.ts:72` is a `Map` keyed by the normalized
  `Host`, written for every host including the ones that resolve to no shop (`:110,182`), with
  a time limit on reads and no limit on size. `lib/tenant/redirects.ts:15` and the region map in
  `middleware.ts:111-114` are keyed by publishable key, which a client cannot invent.
- Risk: a script that sends requests with random `Host` values grows the process until it is
  killed, and the process serves every shop.
- Recommendation: cap the map, dropping the oldest entry past a few thousand, and drop expired
  entries on write.
- Estimate: 1 hour with a test.
- Class: separate task. Check first what the proxy in front forwards for an unknown host.

### D-3. A Read That Failed And A Thing That Is Gone Look The Same To The Caller

- Evidence: `retrieveCart` ends in `.catch(() => null)` (`apps/storefront/src/lib/data/cart.ts:78`),
  `retrieveCustomer` does the same (`lib/data/customer.ts:47`), and the mutations throw through
  `medusaError`, which keeps the message and drops the status (`lib/util/medusa-error.ts:9-28`).
  The port of the stale cart fix in this unit needed a second request for exactly that reason:
  the source dropped the cart cookie on any `null`, and a `null` here also means a backend that
  was down for one second (`lib/data/cart.ts`, `isCartGone`).
- Risk: code that reacts to «gone» by deleting state will sooner or later delete a live cart or
  sign a buyer out on a backend hiccup.
- Recommendation: let the two reads answer a small result, `{ status: "ok" | "gone" | "failed" }`,
  next to the current functions, and move callers that delete state onto it.
- Estimate: 3 hours with tests.
- Class: separate task.

### D-4. The Redirect Table Forgets Itself For A Minute After One Failed Read

- Evidence: `fetchRedirects` answers an empty table on any failure, and `getTenantRedirects` caches
  that answer for sixty seconds (`apps/storefront/src/lib/tenant/redirects.ts:17-44,58-66`). The
  shop lookup next to it keeps the previous answer in the same situation (`lib/tenant/resolve.ts:110-119`).
- Risk: low. Moved pages answer `404` to visitors and crawlers for a minute after one bad
  backend response.
- Recommendation: keep the previous table on failure, the rule `resolve.ts` already follows.
- Estimate: 30 minutes with a test.
- Class: separate task.
