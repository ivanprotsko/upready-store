## How To Read A Finding

Each finding carries the same five fields.

- Evidence: `path:line` in this repository, opened during the review.
- Risk: one sentence, from the point of view of a shop that takes real money.
- Recommendation: what to change.
- Estimate: working time for one engineer who knows the codebase.
- Class: `do now in this unit`, `separate task`, or `needs Ivan's decision`.

Findings are ranked inside a chapter by risk. The cross-chapter ranking is the table in
Ranked Risks, which is rebuilt whenever a chapter lands.

### What Holds

The `/tenants/*` namespace derives the tenant from the authenticated actor and from nothing else.
`getTenantScope` reads `tenant_admin` by `req.auth_context.actor_id`
(`apps/backend/src/api/tenants/tenant-scope.ts:38-63`). Every per-area helper opened so far calls
it instead of reading a tenant id from the request: `products/csv-context.ts:136`,
`marketplace-orders/load-feed.ts:105`, `marketplace-analytics/load-analytics.ts:175`,
`marketplaces/draft-handlers.ts:40`, `notification-settings/helpers.ts:89`,
`requisites/helpers.ts:148`, `marketplace-keys.ts:170,275,320`. A foreign id answers `404`, never
`403`, so a response does not confirm that another shop's row exists (`tenant-scope.ts:17-19`,
`orders/helpers.ts:18-31`).

The routes that move money assert ownership before their workflow runs. All nine
`orders/[id]/**` routes call `assertOwnedOrder`, `payments/[id]/capture` calls
`assertOwnedPayment` (`orders/helpers.ts:22-75`), and the inventory batch route calls
`assertOwnedInventoryItems` (`products/helpers.ts:148`).

Store order reads are scoped to the shop of the publishable key and to the owner or the holder of
the guest token (`apps/backend/src/api/store/order-access.ts:95-132`, wired at
`api/middlewares.ts:1452,1458,1463,1472`). The integration spec covers the cross-shop case
(`apps/backend/integration-tests/http/store-order-isolation.spec.ts:201-206`).

### T-1. The Tenant Order Link Has One Chance To Be Written

- Evidence: `apps/backend/src/subscribers/order-placed-tenant-link.ts:18-20` runs the link
  workflow with no `try`, no retry and no dead-letter record.
  `apps/backend/src/workflows/tenant/link-order-to-tenant/index.ts:21-37` reads the order with
  `throwIfKeyNotFound: true`, so a read that races the order commit throws. No file under
  `apps/backend/src/scripts`, `apps/backend/src/jobs` or `apps/backend/docker-entrypoint.sh`
  mentions the link or the workflow, so nothing converges a missed link. The panel lists orders
  only through that link (`tenant-scope.ts:95-113`). Redis backs the event bus only when
  `REDIS_URL` is set and the process is in production or `USE_REDIS=true`
  (`apps/backend/medusa-config.ts:10,38,42`). Otherwise the bus is in memory and an event that
  was being handled when the process restarted is gone.
- Risk: a customer pays, the handler fails once, and the order never appears in the owner's
  panel, so it is never packed or shipped.
- Recommendation: add an idempotent convergence script `link-orphan-orders` under
  `src/scripts`, wired into `docker-entrypoint.sh` and into a scheduled job, that links every
  order whose sales channel belongs to a tenant and that has no `tenant_order` row. Log a missed
  link at `error` level in the subscriber.
- Estimate: 4 hours with an integration spec.
- Class: separate task. It adds behaviour, so it is not a refactor.

### T-2. Shop Scoping Of Store Orders Fails Open For A Key Without Channels

- Evidence: `apps/backend/src/api/store/order-access.ts:112-120` checks the sales channel only
  inside `if (channelIds.length)`. The list scope at `:179-186` and the transfer guard at
  `:215-231` use the same condition.
- Risk: a publishable key that has lost its sales channel reads across shops again, limited only
  by the owner and guest token rules.
- Recommendation: refuse with `404` when the key names no channel. Check first that a
  single-store install always binds a channel to its key, because that install is the template
  this repository ships.
- Estimate: 1 hour with two spec cases.
- Class: separate task. It changes an answer, so it is not a refactor.

### T-3. Tenant Scoping Is A Convention With No Guard

- Evidence: the only middleware on the namespace authenticates and blocks archived tenants
  (`apps/backend/src/api/middlewares.ts:293-297`). Scoping is left to each of the 145 route
  files under `api/tenants`. 93 import `tenant-scope` directly. The other 52 split three ways.
  In 26 a search found a named ownership call or `req.auth_context.actor_id`. Of those helpers
  only `assertOwnedOrder` and `assertOwnedPayment` were read to their definition, and the rest
  (`assertOwnedMethod`, `getTenantWarehouse`, `listTenantMethods`, `getTenantWithDomains`,
  `getTenantCustomerAggregates`, `assertOwnedPaymentSettings`) are matched by name only so far.
  In 16 the route was opened and delegates to a helper that calls `getTenantScope`: the 12 cited
  under What Holds, both `marketplaces/questions/[id]` routes through `draft-handlers.ts:40`, and
  both `notification-settings/telegram` routes through `ownSettings`. 1 serves a static table
  (`shipping-methods/regions/route.ts`). The last 9 re-export an Admin `GET` handler with no
  tenant filter in the route or in its middleware entry: `collections`, `product-tags`,
  `product-types`, `regions`, `price-preferences`, `shipping-profiles`, `fulfillment-providers`,
  `promotions/rule-attribute-options/[rule_type]` and `shipping-options`. Seven of them list
  platform data. Two list data that shops own, which is finding T-5.
- Risk: a new route that forgets the filter compiles, passes every check and serves one shop's
  data to another.
- Recommendation: a unit spec that walks `api/tenants/**/route.ts` and fails when a file neither
  imports `tenant-scope` nor a helper on a reviewed list, with a named allowlist for the global
  read-only reference lists.
- Estimate: 2 hours.
- Class: do now in this unit. It is a test and changes no behaviour.

### T-5. Two Re-Exported Admin Lists Show One Shop The Data Of Every Shop

Confirmed by reading. Not measured on a stand yet. The two-shop stand built for acceptance line 4
will carry the curl.

- Evidence: `apps/backend/src/api/tenants/shipping-options/route.ts` is one line,
  `export { GET } from "@medusajs/medusa/api/admin/shipping-options/route"`. Its middleware entry
  narrows only by a `stock_location_id` the caller sends (`apps/backend/src/api/middlewares.ts:819-835`),
  so a call without it, or with another shop's location, lists every shop's options. The Admin
  defaults return `*prices`, `data`, `*service_zone` and `*provider`
  (`@medusajs/medusa/dist/api/admin/shipping-options/query-config.js`, `defaultAdminShippingOptionFields`).
  The route comment says options belong to the store and not to a tenant, which stopped being
  true when `shipping-methods/**` became per shop through `getTenantWarehouse`.
  `apps/backend/src/api/tenants/collections/route.ts` re-exports the Admin list the same way
  (`middlewares.ts:497-500`), and collections are created per shop by
  `apps/backend/src/workflows/tenant/seed-tenant-dataset/index.ts:125`.
- Risk: a shop owner reads the delivery prices and provider data of every other shop, and the
  collection titles enumerate the shops on the deployment.
- Recommendation: replace both re-exports with handlers that intersect the list with the
  tenant's own stock locations and collections, the way `listTenantStockLocationIds` already does
  (`tenant-scope.ts:127-149`). Check the write side as well: whether a product update accepts
  another shop's `collection_id` was not read.
- Estimate: 4 hours with seam specs for both lists.
- Class: separate task. It narrows an answer, so it is not a refactor.

### T-4. Every Ownership Check Reads All Order Ids Of The Shop

- Evidence: `listTenantOrderIds` selects `tenant.orders.id` for the whole tenant
  (`apps/backend/src/api/tenants/tenant-scope.ts:95-113`). `assertOwnedOrder` and
  `assertOwnedPayment` then search that array (`orders/helpers.ts:26-28,67-69`). The product,
  category, promotion and campaign checks have the same shape (`tenant-scope.ts:179-191,235-247,
  297-309,336-348`).
- Risk: the order page of a shop with tens of thousands of orders slows down with every sale.
- Recommendation: check one id with one filtered query on the link entity, keeping the helper
  signatures.
- Estimate: 3 hours with the existing seam specs as the safety net.
- Class: separate task. Candidate for Part C if the link entities prove filterable by both keys.

### C-1. No Inventory Event Reaches The Storefront

- Evidence: the product list asks for `+variants.inventory_quantity` under `cache: "force-cache"`
  (`apps/storefront/src/lib/data/products.ts:77-84`). The revalidation subscriber lists no
  `inventory-item.*`, `inventory-level.*` or `reservation-item.*` event
  (`apps/backend/src/subscribers/product-updated.ts:15-40`), and the webhook route has no branch
  for them (`apps/storefront/src/app/api/revalidate/route.ts:38-111`).
- Risk: a product shows as in stock after the last unit was sold, and the shop takes money for
  goods it does not have.
- Recommendation: subscribe to the inventory events and clear the same paths the product branch
  clears.
- Estimate: 2 hours with tests on both sides.
- Class: do now in this unit (recorded defect `t-port-stale-inventory-fix`).

### C-2. Product Type Events Are Sent And Ignored

- Evidence: the subscriber sends `product-type.updated`, `.created` and `.deleted`
  (`apps/backend/src/subscribers/product-updated.ts:19-21`). The route matches product, variant,
  tag and option events and no product type event
  (`apps/storefront/src/app/api/revalidate/route.ts:38-51`), so it answers `revalidated: true`
  having cleared nothing (`route.ts:192`).
- Risk: a renamed product type keeps its old name on the storefront until the process restarts.
- Recommendation: add the three events to the product branch. Make the route answer with what it
  cleared, so an unknown type is visible in the backend log.
- Estimate: 1 hour.
- Class: do now in this unit (recorded defect `t-revalidate-product-type-gap`).
