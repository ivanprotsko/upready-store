## How To Read A Finding

Each finding carries the same five fields.

- Evidence: `path:line` in this repository, opened during the review.
- Risk: one sentence, from the point of view of a shop that takes real money.
- Recommendation: what to change.
- Estimate: working time for one engineer who knows the codebase.
- Class: `do now in this unit`, `separate task`, or `needs Ivan's decision`.

Findings are ranked inside a chapter by risk. The cross-chapter ranking is the table in
Ranked Risks, which is rebuilt whenever a chapter lands.

### What Holds

The `/tenants/*` namespace derives the tenant from the authenticated actor and from nothing else.
`getTenantScope` reads `tenant_admin` by `req.auth_context.actor_id`
(`apps/backend/src/api/tenants/tenant-scope.ts:38-63`). Every per-area helper opened so far calls
it instead of reading a tenant id from the request: `products/csv-context.ts:136`,
`marketplace-orders/load-feed.ts:105`, `marketplace-analytics/load-analytics.ts:175`,
`marketplaces/draft-handlers.ts:40`, `notification-settings/helpers.ts:89`,
`requisites/helpers.ts:148`, `marketplace-keys.ts:170,275,320`. A foreign id answers `404`, never
`403`, so a response does not confirm that another shop's row exists (`tenant-scope.ts:17-19`,
`orders/helpers.ts:18-31`).

The routes that move money assert ownership before their workflow runs. All nine
`orders/[id]/**` routes call `assertOwnedOrder`, `payments/[id]/capture` calls
`assertOwnedPayment` (`orders/helpers.ts:22-75`), and the inventory batch route calls
`assertOwnedInventoryItems` (`products/helpers.ts:148`).

Store order reads are scoped to the shop of the publishable key and to the owner or the holder of
the guest token (`apps/backend/src/api/store/order-access.ts:95-132`, wired at
`api/middlewares.ts:1452,1458,1463,1472`). The integration spec covers the cross-shop case
(`apps/backend/integration-tests/http/store-order-isolation.spec.ts:201-206`).

The `/store/tenant/*` routes take the shop from the sales channel of the publishable key and
answer `404` for a key with no tenant behind it, so they fail closed
(`apps/backend/src/api/store/tenant/resolve-tenant.ts:17-32`). The guest order claim refuses a key
with no channel the same way (`api/store/customers/me/claim-orders/route.ts:37-48`), which is the
behaviour T-2 asks of the order reads.

The six ownership helpers an earlier pass had matched by name only were opened, and each takes its
scope from the actor. `getTenantWarehouse` and `assertOwnedPaymentSettings` call `getTenantScope`
(`shipping-methods/helpers.ts:54-55`, `payment-settings/helpers.ts:80-84`). `listTenantMethods` and
`assertOwnedMethod` filter by the service zones of that warehouse (`shipping-methods/helpers.ts:255-285`).
`getTenantCustomerAggregates` starts from `listTenantOrderIds` (`customers/helpers.ts:72-75`).
`getTenantWithDomains` reads `tenant_admin` by `req.auth_context.actor_id` itself
(`domains/helpers.ts:25-45`), the one copy of that read outside `getTenantScope`.

The platform routes under `/admin/tenants` carry only validators in `api/middlewares.ts:1296-1331`
and rely on the framework's default `/admin/*` authentication for the actor type `user`, so a
`tenant_admin` token does not open them. `GET /storefront/by-host` is public by design and answers
the publishable key, which every storefront page already sends (`api/storefront/by-host/route.ts:19-22,150-170`).
Uploads from the panel are stored under `tenants/<tenant id>/` taken from the actor, not from the
request (`api/tenants/uploads/route.ts:38-44`).

### T-1. The Tenant Order Link Has One Chance To Be Written

- Evidence: `apps/backend/src/subscribers/order-placed-tenant-link.ts:18-20` runs the link
  workflow with no `try`, no retry and no dead-letter record.
  `apps/backend/src/workflows/tenant/link-order-to-tenant/index.ts:21-37` reads the order with
  `throwIfKeyNotFound: true`, so a read that races the order commit throws. No file under
  `apps/backend/src/scripts`, `apps/backend/src/jobs` or `apps/backend/docker-entrypoint.sh`
  mentions the link or the workflow, so nothing converges a missed link. The panel lists orders
  only through that link (`tenant-scope.ts:95-113`). Redis backs the event bus only when
  `REDIS_URL` is set and the process is in production or `USE_REDIS=true`
  (`apps/backend/medusa-config.ts:10,38,42`). Otherwise the bus is in memory and an event that
  was being handled when the process restarted is gone.
- Risk: a customer pays, the handler fails once, and the order never appears in the owner's
  panel, so it is never packed or shipped.
- Recommendation: add an idempotent convergence script `link-orphan-orders` under
  `src/scripts`, wired into `docker-entrypoint.sh` and into a scheduled job, that links every
  order whose sales channel belongs to a tenant and that has no `tenant_order` row. Log a missed
  link at `error` level in the subscriber.
- Estimate: 4 hours with an integration spec.
- Class: separate task. It adds behaviour, so it is not a refactor.

### T-6. A Caller Chooses The Fields, And The Tenant Link Is Not On Any Block List

Found by reading, then measured on the two-shop stand of this unit on 2026-09-21 (backend on
port 9341, shops `acme` and `globex`, one buyer with one order in each shop). All three requests
answered with data.

- Measured: (1) `GET /store/products?limit=1&fields=id,*tenant,*tenant.admins,*tenant.requisites`
  with the shop's publishable key and no login answered 200 with the tenant row and
  `admins: [{ email: "admin@acme.test", first_name, last_name, ... }]`. The same caller read
  `*tenant.notification_settings` in full: `telegram_chat_id`, `link_code`,
  `link_code_expires_at`, `email_reply_to` and the text of the last delivery error. (2)
  `GET /tenants/orders/<order of A>?fields=id,*customer.orders` as the owner of `acme` answered 200
  with two orders, and the second is the order the buyer placed in `globex`, with its e-mail,
  region and sales channel. (3) `GET /tenants/products/<own id>?fields=id,*sales_channels.tenant.admins`
  answered with the admin rows as well. A fourth probe, `*tenant.sales_channels.orders` on the
  Store API, came back empty, so the Store API list of Medusa does hold for `orders`.

- Evidence: 40 route files under `apps/backend/src/api/tenants` hand `req.queryConfig.fields` to
  the query, and their middleware entries borrow the Admin query configs, for example
  `api/middlewares.ts:701-705` for `apps/backend/src/api/tenants/orders/[id]/route.ts:16-20`. Of the
  18 Admin query configs checked, only `customers`, `promotions` and `product-categories` carry an
  `allowed` list (`@medusajs/medusa/dist/api/admin/*/query-config.js`). `orders`, `payments`,
  `products`, `campaigns`, `sales-channels`, `stock-locations`, `stores`, `inventory-items`,
  `reservations`, `returns`, `claims`, `exchanges`, `collections`, `shipping-options` and `regions`
  carry none, and no entry under `/tenants` adds one. The ownership check covers the id in the
  path. It does not cover a relation asked for through `?fields=`. If the order to customer link
  resolves in both directions, `fields=*customer.orders` on the shop's own order names the orders
  the same buyer placed in every other shop. Medusa 2.19 knows this class of request and strips `orders`, `carts`,
  `customer` and the payment relations on the public Store API
  (`@medusajs/medusa/dist/api/store/utils/disallowed-fields.js`), and the framework sets restricted
  fields only for `/store` and `/admin` (`@medusajs/framework/dist/http/router.js:232-241`), so
  `/tenants` gets neither list. The Store API list knows nothing of this repository's own links
  either: `apps/backend/src/links/tenant-product.ts` makes `tenant` a relation of every product,
  and the tenant model hangs `admins`, `requisites`, `notification_settings`, `domains` and
  `integration_secrets` off it (`apps/backend/src/modules/tenant/models/tenant.ts:36-93`). The
  secret payloads are AES-256-GCM ciphertext (`models/tenant-integration-secret.ts:62`), so a read
  would not hand over a usable key.
- Risk: a shop owner reads what a buyer ordered in every other shop. An anonymous visitor holding
  the public key, which every page of the storefront carries, reads the owner's name and e-mail,
  the legal requisites and the notification settings of the shop. A pending Telegram `link_code`
  read this way lets a stranger link their own chat and receive the shop's order notifications.
  This is the same class as defect 8 of this unit, through a door that defect did not name.
- Recommendation: give every `/tenants` entry a `disallowed` list (`tenant`, `orders`, `carts`,
  `customer.orders`) through one shared wrapper around `validateAndTransformQuery`, and add
  `tenant` to the Store API through `projectConfig.http.restrictedFields.store`. Pin each of the
  three requests above in an integration spec that expects no `admins`, no
  `notification_settings` and one order. Rotate any Telegram link code that is pending on the live
  host once the fix is deployed.
- Estimate: 6 hours for the wrapper, the config line and the specs.
- Class: separate task, and the first one to schedule. It narrows answers, so it is not a
  refactor, and this unit's brief limits fixes to the nine recorded defects.

- Evidence: `apps/backend/src/api/tenants/customers/[id]/route.ts:11-13` states that a customer is

  buyer account should be one per platform or one per shop is a product decision, listed under
  Decisions For Ivan.
- Estimate: 2 hours for the narrowing with a seam spec.
- Class: needs Ivan's decision for the account model. The narrowing is a separate task.

### How The Cache Is Keyed And Cleared

A cached read is a `fetch` with `cache: "force-cache"` and no `revalidate` period, so an entry
lives until something clears it. The catalog tags are built per visitor and per shop:
`getCacheOptions` answers `<tag>-<_medusa_cache_id>-<handle>`
(`apps/storefront/src/lib/data/cookies.ts:169-190`). The webhook cannot know a visitor's cache id,
so `revalidateTag("products")` in the route matches only the three reads that use the bare tag,
the sitemap and `llms.txt` (`apps/storefront/src/app/sitemap.ts:71,103,136`,
`app/llms.txt/route.ts:69,81,96`). Catalog pages are cleared by `revalidatePath`, and a path is
one path for every shop on the process (`app/api/revalidate/route.ts:10-21`). The tenant document
tags (`tenant-home-<handle>`, `tenant-pages`, `tenant-articles`, `product-attributes`,
`product-reviews`) carry no visitor id and are cleared by tag.

## Chapter 8. Deploy And Operability

Status: READ from the repository only: `deploy/compose.mt.yml`, `apps/backend/docker-entrypoint.sh`,
`apps/backend/medusa-config.ts` and `deploy/scripts`. The live host is off limits for this unit,
so nothing here says what runs there, only what the repository would start.

### What Holds

Every service of the multi-tenant stack has a health check and starts after the one it needs
(`deploy/compose.mt.yml:20-25,40,59-61,150,196-198,232,282-291`). Owner uploads live on a host path
outside the image, with the reason written next to the mount (`:144-147`). The backend entry point
migrates and converges its seed data on every start, and each script is written to do nothing on
a second run (`apps/backend/docker-entrypoint.sh`). The revalidation sender logs a call that did
not clear anything at `error` level with the status (`apps/backend/src/storefront-revalidate/index.ts:54-60`).

### O-1. The Multi-Tenant Stack Starts Without Redis, So Events And Workflows Live In Memory

- Evidence: `deploy/compose.mt.yml` defines `postgres`, `backend`, `storefront`, `panel`, `ingress`
  and `coolify`, and neither a Redis service nor `REDIS_URL`. `apps/backend/medusa-config.ts:6-10,32-44`
  loads the Redis event bus, workflow engine and cache only when `REDIS_URL` is set.
- Risk: an event that is being handled when the backend restarts is gone, and with it the link of
  a paid order to its shop (finding T-1), the order e-mail, the Telegram notice and the storefront
  revalidation (finding C-3). Every deploy is such a restart. A second backend replica is also
  impossible, because two processes would not share events or locks.
- Recommendation: add Redis to the stack with a volume and set `REDIS_URL`. Together with the
  convergence script of T-1 this closes the lost order path from both ends.
- Estimate: 3 hours with a restart test on the stand: place an order, restart the backend during
  the subscriber, check the link and the e-mail.
- Class: needs Ivan's decision, because it adds a service to the live host. The work is a
  separate task.

### O-2. A Start Can Be Green While Payment Is Off For Every Shop

- Evidence: three entry point scripts run under `set +e`, and a failure prints a `WARNING` line
  and the start goes on. One of the lines reads «the checkout will not offer Robokassa to any
  shop» (`apps/backend/docker-entrypoint.sh:88-112`, the blocks for `rename-default-shipping-methods.js`,
  `backfill-tenant-redirects.js` and `link-robokassa-regions.js`). The health check asks
  only `/health` (`deploy/compose.mt.yml:21`).
- Risk: a deploy reports healthy, and the first person to learn that no shop can take a card is a
  buyer.
- Recommendation: keep the soft failure, because a hard one would take every shop down for one
  script. Write the result of each script to a row or a file that a `/health/deep` route reports,
  and have the deploy script read it and print it in red.
- Estimate: 3 hours.
- Class: separate task.

### O-3. The Repository Describes No Scheduled Backup Of The Shared Database Or Of Uploads

- Evidence: the only `pg_dump` in `deploy/` is the one `deploy-stand.sh --fresh-db` takes before it
  drops a single-store stand (`deploy/scripts/deploy-stand.sh:136-138`). `deploy/README.md` records
  a stand database that was dropped twice (`:627-631`). Nothing in `deploy/` dumps the
  multi-tenant database or copies `media-tenants`.
- Risk: every shop shares one database and one uploads folder, so one bad migration or one wrong
  `down -v` loses all of them at once.
- Recommendation: a nightly `pg_dump` and an `rsync` of the uploads path to storage outside the
  host, with a restore drill recorded in `deploy/README.md`. If this already runs on the host
  outside the repository, write it down here, because an agent reading the repository will
  assume it does not exist.
- Estimate: 3 hours.
- Class: needs Ivan's decision, because only he can say what the host already does.

## Chapter 10. Security Basics

Status: READ for configuration, the webhook, uploads and the auth entries of
`api/middlewares.ts`. No request was sent anywhere. Tenant isolation is chapter 1 and is not
repeated here.

### What Holds

Integration credentials are stored as AES-256-GCM ciphertext under a key from the environment
(`apps/backend/src/modules/tenant/models/tenant-integration-secret.ts:62`, `src/tenant-secrets/crypto.ts`),
and the stack passes every secret from the environment with no default in the compose file
(`deploy/compose.mt.yml:66-69`). The revalidation webhook compares a shared secret
(`apps/storefront/src/app/api/revalidate/route.ts:27-34`). An archived shop is locked out at login
and on every panel route (`apps/backend/src/api/middlewares.ts:293-304`). The session cookie stays
`lax`, which the payment return needs, and `AGENTS.md` says why.

### S-1. Real Tokens Sit In A Tracked Document

- Evidence: `artifacts/docs/2026-09-10-mt-vendors-acceptance.md` is the one tracked file that
  matches the shape of a signed JWT, on three lines
  (`artifacts/docs/2026-09-10-mt-vendors-acceptance.md:106,110,227`). Only the line numbers were
  printed. The values were not opened or copied for this review.
- Risk: anyone with read access to the repository or to a clone holds a token that was valid on
  the day of that acceptance, signed with a secret that may still be in use.
- Recommendation: rotate `JWT_SECRET` and `COOKIE_SECRET` on every stand the document touched,
  which ends the tokens whatever git keeps. Then replace the values in the file with a
  placeholder. Do not rewrite history.
- Estimate: 1 hour, plus a sign-in again for every user of those stands.
- Class: needs Ivan's decision, because rotation signs everyone out.

### S-2. The Backend Starts With A Known Signing Secret When The Variable Is Missing

- Evidence: `apps/backend/medusa-config.ts:155-156` falls back to `"supersecret"` for `jwtSecret`
  and `cookieSecret`, and `:108-109` does the same for the signed state of the Yandex login. The
  compose file passes `${JWT_SECRET}` with no default (`deploy/compose.mt.yml:66-67`), so an env
  file that lacks the line yields an empty string, and the fallback wins without a word in the
  log.
- Risk: on such a start anyone can sign a token for any actor, a platform administrator
  included.
- Recommendation: refuse to start in production when either secret is missing or equals the
  fallback. Keep the fallback for development only.
- Estimate: 1 hour with a unit test on the config function.
- Class: separate task. It changes start-up behaviour.

### S-3. The Revalidation Webhook Is Open When Its Secret Is Not Set

- Evidence: the route checks the header only `if (process.env.REVALIDATE_SECRET && ...)`
  (`apps/storefront/src/app/api/revalidate/route.ts:29-34`), and the route is public on every shop
  domain, because `/api` is outside the middleware matcher (`apps/storefront/src/middleware.ts`,
  `config.matcher`).
- Risk: with the variable missing, anyone can clear the rendered pages of every shop in a loop
  and turn the cache off for the whole process (finding C-4 describes the cost of one call).
- Recommendation: answer `503` in production when the secret is not configured, the way the
  settings route already refuses a write without its secret
  (`apps/backend/src/api/store/storefront-settings/route.ts:39-52`).
- Estimate: 30 minutes with a test next to the existing route test.
- Class: separate task. It changes an answer.

### S-4. A Shop Owner Uploads Any File Type To A Public Address

- Evidence: `POST /tenants/uploads` uses the Admin's upload middleware unchanged
  (`apps/backend/src/api/middlewares.ts:452-455`) and stores every file with `access: "public"`
  under its original name (`apps/backend/src/api/tenants/uploads/route.ts:41-50`). The Admin trusts
  its users. The panel's users register themselves (`middlewares.ts:283-290`).
- Measured on the stand on 2026-09-21: the owner of `acme` posted `probe.html` with a script in
  it, got `files[0].url` under `/static/tenants/<tenant id>/`, and the backend served it with
  `200` and `Content-Type: text/html; charset=UTF-8`, with no `Content-Disposition`, no
  `X-Content-Type-Options` and no content security policy. The stand uses the local file
  provider. What the live file host answers was not measured, because live is off limits.
- Risk: an owner uploads an HTML or SVG file with a script in it and gets a public address for it
  on the platform's own host, where a browser runs it on the platform's origin.
- Recommendation: an allowlist of image types and a size limit on the panel route, and a
  generated file name. Serve `/static` with `X-Content-Type-Options: nosniff` and
  `Content-Disposition: attachment` for everything that is not an image.
- Estimate: 2 hours with a seam spec.
- Class: separate task.

### S-5. Nothing In The Repository Limits Login Attempts

- Evidence: a search of `apps/backend/src/api` finds no rate limit on `/auth/tenant/emailpass`,
  on the customer login or on the password reset. The one entry for the owner login refuses an
  archived shop and counts nothing (`apps/backend/src/api/middlewares.ts:298-304`). The proxy
  labels of the backend define a redirect to https and no other middleware
  (`deploy/compose.mt.yml:157-170`), and the files under `deploy/mt` define none.
- Risk: password guessing against shop owners and buyers runs at the speed of the backend.
- Recommendation: a rate limit at the proxy for `/auth/*`, per address, as the cheapest first
  step.
- Estimate: 2 hours with a measurement on the stand.
- Class: separate task.
