## 1. Цель и границы

Витрина перестраивается так, чтобы макеты страниц, компоненты, темы и анимации описывались JSON и рендерились в рантайме движком app-shell (`@ivanprotsko-org/renderer`, документ экрана AppUISpec v0, реестр контрактов `upready.component-contract/v0`). Движок не изобретаем, только потребляем. Продукт остаётся рабочим на каждом промежуточном шаге и не мешает текущей разработке.

Три задачи Ивана в порядке исполнения:

1. **Независимость от Medusa UI** сначала через обёртки, потом через собственные реализации.
2. **Собственные компоненты** волнами по графику, с тестами.
3. **Рендер UI из JSON** постранично, когда компоненты целиком наши.

| 3. Матрица и эталоны | нет | `matrix.json` (варианты × состояния × субкомпоненты) + `golden.json` (измерения) + галерея `/[locale]/ui-lab/<component>` только в dev | Ф1 |
| 4. Тесты стыков | нет | Playwright e2e в Docker + vitest для `lib/data`, middleware; jest бэкенда для custom routes | Ф1, параллельно |

Принцип, который держит всю цепочку: **обёртка стабилизирует API, контракт стабилизирует JSON, эталоны стабилизируют вид.** Три вещи, которые не меняются, когда под ними меняется реализация.

## 4. Фазы и волны

### Ф1.0 Фундамент (оркестратор A, T0–T1)
- T0 реестр компонентов: `apps/storefront/scripts/ui-inventory.mjs` → `specs/design-system/ui-inventory.json` (схема `ui-inventory.schema.json`). Парсер, не grep. Гейт: итоги = таблице §2.
- T1 каркас: `src/ui/`, alias, ESLint-правило как `warn` (в `error` переводится в Ф1.3, когда прямых импортов вне `src/ui` станет 0), галерея `ui-lab` за env-флагом, Playwright в Docker с общим раннером измерений. Playwright ставится ПЕРВЫМ маленьким PR в `dev`, потому что оркестратор B тоже от него зависит.

### Ф1.1 Пилот: семь компонентов, четыре агента Opus (оркестратор A, T2)
Состав по Ивану: A1 icon + badge + tooltip · A2 select + otp-input · A3 date-picker · A4 dropdown-menu. Цель пилота — подводные камни составных компонентов: состояния перемножаются на состояния субкомпонентов и вариантов. Каждый агент сдаёт обёртку, контракт, матрицу, эталоны, страницу галереи, перенос существующих вызовов и список камней.
Замечание архитектора: tooltip, otp-input и date-picker в витрине не используются вовсе, select и dropdown-menu по одному разу. Их обёртки — учебный полигон, а не миграция: приёмка «вызовы перенесены» для них пустая. Состав оставлен как приказал Иван, потому что именно эти компоненты самые составные.
Решение по иконкам: обёртка `Icon` принимает `name` строкой и держит явную карту из 30 используемых иконок. Строка сериализуется в JSON, явная карта сохраняет tree-shaking.

### Ф1.2 Тесты пилота (агент Fable, T3, стартует по завершении T2)
Полнота контрактов, матрицы на каждое сочетание вариант × состояние × субкомпонент, клавиатура и a11y для составных, mutation-proof: сломанный токен даёт красный.

### Ф1.3 Волна high-usage (оркестратор A после приёмки пилота)
Text, Button, Heading, Container, Checkbox, RadioGroup, Label, Table, Input, StatusBadge, IconButton, IconBadge, `clx`. Порядок по убыванию числа файлов. Финал: 0 прямых импортов вне `src/ui`, ESLint-правило в `error`, allowlist Tailwind генерируется из контрактов.

### Ф1 параллельно: тесты стыков (оркестратор B)
Входы и выходы витрины: роуты, `lib/data/*`, middleware локали и региона, cookies, `api/*`, custom routes бэкенда, workflows, subscribers, письма. Стыки: человек — интерфейс (Playwright), интерфейс — сервер (vitest + jest), плюс то, что оркестратор сочтёт нужным и обоснует замером. Задокументированные баги medusajs и gorgojs — в `artifacts/research/`.

### Ф2 Собственные компоненты волнами
Старт после Ф1.3 и решения развилки F1 (§5). Волна = 2–4 компонента по убыванию использования, реализация меняется за обёрткой, эталоны Ф1 не меняются. Каждая волна — своя ветка, worktree, PR в `dev`, приёмка глазами Ивана на `:8000`.

### Ф3 Рендер из JSON
Контракты обёрток отображаются на реестр app-shell, пилотная страница рендерится из AppUISpec через `@ivanprotsko-org/renderer`, потом страницы по одной. Зависит от среза 4 роадмапа app-shell (`docs/ROADMAP-JSON-UI.md`: «целые экраны из JSON»).

## 5. Развилки

**F1, Ивану, блокирует только Ф2.** Чем станут «свои» компоненты.
- (a) Принять `@ivanprotsko-org/ui` из app-shell (shadcn, Tailwind v4) как базу и расширять его компонентами магазина. Плюс: renderer уже зависит от него, одна библиотека на студию и магазины. Минус: витрина на Tailwind v3 и preset Medusa, переход на v4 — отдельная волна.
- (b) Свой пакет `@ivanprotsko-org/store-ui` на нынешнем Tailwind v3. Плюс: без миграции Tailwind. Минус: третья библиотека, контракты придётся мапить дважды.
- (c) `ui-kit` по доктрине (custom elements, light DOM). Плюс: канон workspace. Минус: React-витрина и renderer его не потребляют напрямую.
Рекомендация: (a). Вопрос заведён как `q-ds-target-library`.

**F2, решено.** Обёртки живут в `src/ui/<name>/`, а не в `modules/common/components/ui` как в upstream. Upstream-шимы покрывают другие компоненты, совместимость портов от этого не растёт, зато `src/ui` даёт чистую границу для ESLint.

**F3, решено.** Проверка вариантов: галерея-роут в самой витрине + Playwright в Docker + измерения в JSON. Скриншот пишется как улика, но сравнение идёт по измерениям: размер, цвет, фон, тень, радиус, типографика, каждое отдельно, как просил Иван. Отклонено: Storybook (второй рантайм и своя сборка), Playwright component testing (не дружит с App Router и серверными компонентами). Браузер из bash-инструмента на macOS не стартует (`~/upready/specs/playwright-ui-testing-spec.md`), поэтому Docker-образ Playwright, версия образа = версии пакета.

**F4, решено.** Состав пилота по списку Ивана, см. §4 Ф1.1.

**F5, решено.** Ветки: `dev` в основном checkout (Иван смотрит `:8000` отсюда), feature-ветки в `~/upready/worktrees/upready-store/<branch>` со своими портами (A `:8001`, B `:8002`), бэкенд общий. `feature → dev` мержит оркестратор после приёмки архитектора. `dev → stage → main` только по команде Ивана (правила 21b/21c).

**F6, решено.** Гейт границы двухслойный: ESLint `no-restricted-imports` (в `next lint`, который гоняет `next build`) плюс число прямых импортов в `ui-inventory.json`. Число в отчёте каждой волны копируется из вывода скрипта.

## 7. Кто что делает и почём

Цепочка по правилу 3c: архитектор (эта сессия) → оркестратор A `store-ui-a` (Opus, ultracode) → четыре агента Opus + агент Fable; оркестратор B `store-seams-b` (Fable, ultracode) → субагенты Sonnet/Opus по правилу 5e.

Оценка токенов на Ф1.0–Ф1.2 (замеры правила 25d: старт агента ≈20k, запись кэша ≈80k, порция Ивана 100–125k на агента):

| Кто | Штук | Токенов на единицу | Итого |
|---|---|---|---|
| Агенты Opus пилота | 4 | 100–125k | 400–500k |
| Агент Fable тестов | 1 | 125–150k | 125–150k |
| Оркестратор A сам | 1 | 200–300k | 200–300k |
| Оркестратор B + субагенты | 1 + 3–5 | 300–400k + 5×60k | 600–700k |
| **Всего Ф1.0–Ф1.2 и стыки** | | | **≈1,3–1,7 млн** |

План даунгрейда (правило 3b): T0-скрипт и любая партия ≥5 однотипных файлов — Sonnet; агент, вышедший за 125k без сдачи, делится по компонентам; Docker Playwright не завёлся — эталоны снимает Иван в Terminal.app (путь 3 спеки), тесты не откладываются; оркестратор B при нехватке окна сдаёт стык «интерфейс — сервер» первым, потому что он на существующем jest.

## 8. Риски

- **Allowlist Tailwind.** Новый компонент без глоба рендерится без стилей и без ошибки. `Select` уже в этом состоянии. Пилот A2 проверяет живым рендером и чинит; Ф1.3 переводит allowlist на генерацию из контрактов.
- **Дрейф preset.** Обновление `@medusajs/ui-preset` меняет токены под обёртками. Версии пиннятся точно, эталоны ловят дрейф.
- **Локали.** 36 каталогов без гейта паритета. Обёртки не вводят новых строк; если вводят, скрипт паритета из AGENTS.md обязателен в том же коммите.
- **Порты.** `:8000` принадлежит Ивану. Worktree поднимают свои порты, backend не дублируют.
- **Роль.** Архитектор не пишет код и не спавнит агентов (hook `role-scope-guard`). Всё исполнение в брифах.

## 10. Ревизия 2026-09-06 после ревью архитектора app-shell

Источник: `~/upready/projects/app-shell/artifacts/deliverables/storefront-json-ui-brief-review-2026-09-06.md`, передано Иваном с приказом перестроить план по его §11. Этот раздел главнее §4, §5 F4, §6, §7 там, где противоречит им.

### 10.1 Новые факты из ревью, которые меняют план

- Пакеты движка распространяются как raw TS под Tailwind **v4** через `@source`; потребителей на Next.js у app-shell ноль. Пока витрина на Tailwind 3.4.19, ни один пакет app-shell в неё не встанет, и обёртки остались бы обёртками без шва к движку.
- `@medusajs/ui` 4.2.1 объявляет peer `react ^18.3.1`, витрина гоняет его на React 19 вне peer. Риск фиксируется в реестре и работает доводом за раннюю замену.
- Уровень «экран» AppUISpec v0 принят, но интерпретатор экрана не опубликован; block-gen знает `product-grid`, `site-header`, `site-footer`, `faq`, `hero`, `pricing`, `testimonials`. Задача 3 планируется после публикации уровня экрана, а не «после наших компонентов».
- В разметке витрины 26 разных классов `ui-*` медузы; канон workspace = Geist. Тема из JSON требует одного словаря.
- Tooltip, OTP Input, DatePicker, Calendar в коде витрины отсутствуют полностью, подтверждено вторым замером.

### 10.2 Порядок волн (заменяет §4)

**Шаг 0, до раздачи агентам** (оркестратор A, задача `t-ds-0-foundation`):
1. Ветки: `stage` от `dev`; push `dev` после ответа на `q-store-remote` (origin сейчас = публичный форк gorgojs).
2. Тест-тулинг: Playwright в Docker + vitest, до любой правки кода.
3. Реестр компонентов JSON через TypeScript compiler API с полем `propsUsed` на каждый call-site (алиасы, re-export, spread учитываются). Реестр сужает матрицу: «используемые сочетания + контрактный минимум», не декартово произведение документации. Полный интерфейс берётся из `.d.ts` пакета, документация вторична.
4. Страницы-матрицы и эталоны на v3 для 16 экспортов и 30 иконок из реестра: это базовая линия для следующего пункта.
5. Миграция Tailwind 3.4.19 → v4 со скриншотной и измерительной приёмкой против базовой линии п. 4. Совместимость `@medusajs/ui-preset` 2.19 с v4 выясняется из исходников preset в `node_modules`, а не из памяти.
6. JSON-карта `ui-* → токен канона` для 26 классов. Имена токенов канона фиксируются сейчас, значения зависят от развилки `q-ds-visual-canon`; карта не ждёт ответа.
7. Next-смоук: минимальный стенд ставит `@ivanprotsko-org/renderer` + `block-gen` из GitHub Packages (`.npmrc` со scope, `GITHUB_ACCESS_TOKEN` из `~/upready/.env.keys`), `transpilePackages`, `'use client'`-барьер вокруг `UniversalBlock`, Tailwind v4 `@source` на `node_modules/@ivanprotsko-org/*`, рендерит `product-grid` на живых товарах с бэкенда и снимает кадр.

**Задача 1** (оркестратор A, `t-ds-1-ui-wrappers-pilot`, стартует после шага 0): barrel `src/ui/` + линтер границы, обёртки для набора **из реестра по убыванию частоты** (Text, Button, Heading, Container, Checkbox, Badge, RadioGroup, Label, Input, Table, StatusBadge, IconButton, IconBadge + `clx` + 30 иконок), составные с перемножением состояний (Select, DropdownMenu, Table на @tanstack) второй волной. Группы агентов нарезает оркестратор по реестру, а не по списку из первого брифа.

**Задача 1.2** параллельно (оркестратор B): без изменений плюс §10.4.

**Задача 2**: замена реализации волнами по убыванию частоты из реестра, API обёрток не меняется. Ждёт `q-ds-visual-canon` и `q-ds-target-library`.

**Задача 3**: после публикации уровня экрана из app-shell. В JSON: раскладка, карточки, сетки товаров, hero, header/footer, FAQ, отзывы. В код за `code/*`: PDP-галерея, селектор вариантов, корзина, checkout, адресные формы. Обработчики только именами `action:*`, `showIf` одно сравнение, всё сложнее отдаёт query готовым значением. Анимации только именованными классами и токенами до проектирования слоя `motion`.

### 10.3 Обёртка = шов (уточняет §3 слой 1 и §5 F2)

- API обёртки в осях примитивов app-shell (`variant`, `size`, `tone`, слоты как children или именованные), не в терминах медузы; `appShell.mapping` = `adapter` с описанием перевода пропсов. Поверхность API = `propsUsed` из реестра + контрактный минимум.
