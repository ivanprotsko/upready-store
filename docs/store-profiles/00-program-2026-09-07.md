## 1. Цель и границы

Десять «профилей магазина» на одной кодовой базе upready-store. У каждого свой каталог (товарная категория), свои фото товаров (генерация), свои тексты (заголовки, описания, характеристики, опции и варианты), своя цветовая тема и типографика, своя графика (hero-баннер главной, плитки категорий, промо-строка). Назначение — примеры работ: каждая версия должна читаться как живой магазин бренда, а не как демо стартера.

Порядок Ивана: первый профиль до результата автономно → проверка Ивана глазами → остальные девять тем же конвейером.

Вне программы: публичный деплой десяти версий (отдельное решение после пилота, §11), варианты карточек T0j и панель настроек T0i (волна 2), Tailwind v4 (T0e, отложен решением 2026-09-06).

## 3. Решение: профиль магазина = каталог данных + пресет темы

```
apps/backend/src/migration-scripts/data/profiles/<id>/
  profile.json            upready.store-profile/v0  — бренд, тема, раскладка, блоки главной, счётчики
  catalog/categories.json, product-options.json, products.json, collections.json
                          форма сида; products — upready.store-profile-products/v0 (price_usd, specs, imageBrief)
  theme.json              upready.theme-preset/v0 — значения канон-словаря, light+dark
  i18n/en.json, de.json, fr.json, es.json, ru.json   — переводы каталога в форме сида
  media/manifest.json     upready.store-media-manifest/v0 — каждый рендер: модель, промпт, параметры, sha256, цена, статус
  media/*.webp            доставленные файлы (gitignore); сырьё — artifacts/media/<id>/raw/ (gitignore, не удалять)
  design/style-board.md   стадия дизайна: палитра, шрифты, фотонаправление, ASCII-макеты главной/листинга/PDP
```

Переключение: бэкенд/сид — `STORE_PROFILE=<id>` (нет переменной = сегодняшнее поведение, ноль регрессии); витрина — `NEXT_PUBLIC_STORE_PROFILE=<id>` (скрипт сборки читает `profile.json`+`theme.json` профиля, пишет `src/styles/themes.css` и `src/lib/profile/profile.generated.json`; при отсутствии каталога бэкенда — профиль `default`); медиа — `STORE_MEDIA_BASE_URL` (локально `http://localhost:9023/static/store-profiles/<id>`, на деплое — хост R2/S3).

Что меняется в коде (всё — оркестратору, §7): сид — выбор каталога данных по `STORE_PROFILE`, цены из `price_usd` × таблица отношений, слияние `i18n` профиля поверх базового, имя магазина из бренда, префикс медиа; витрина — имя сайта из профиля, `data-theme`/`data-mode` по умолчанию из профиля + pre-paint скрипт, блок hero профиля, блок плиток категорий, промо-строка из профиля, пропорция `image-frame` из профиля, шрифтовая пара из allow-list через `next/font`; мост 88 переменных Medusa UI → канон-словарь (T0h.1–T0h.4 из брифа theme-presets-panel) — один раз; скрипты `store-profile:validate` и `store-profile:up <id>` (БД, миграции, сид, копирование медиа в static, запуск бэкенда и витрины на портах профиля).

## 6. Роли субагентов и модель

Модель каждого субагента — не ниже Opus (слово Ивана; правило 5e уступает). Оркестратор — новая сессия на Opus (ultracode), промпты агентам — на английском (3a).

## 7. Порядок работ пилота

S0 подготовка (оркестратор) → S1 фундамент, три параллельные зоны без пересечения файлов: (a) профиль в сиде + скрипты, (b) мост темы + шрифты, (c) блоки витрины (сначала стадия дизайна) → S2 style board `sneakers` (креативный директор) → S3 каталог + image brief (мерчендайзер) → S4 изображения: стилевой гейт на одном товаре → батч по одному hero-кадру на товар → один баннер и четыре плитки → манифест (продюсер) → S5 сверка текстов с рендерами (мерчендайзер) → S6 `theme.json`, сборка, сид в `upready_store_sneakers`, запуск `:9023`/`:8028` (инженер темы + инженер профиля) → S7 верификация (верификатор) → S8 передача архитектору. S2 и S3 идут параллельно S1; S4 ждёт S2+S3; S6 ждёт S1+S4+S5. Полные заказы стадий, бюджеты и гейты — в брифе.

## 10. Границы и риски
