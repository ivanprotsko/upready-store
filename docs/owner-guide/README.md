# Документация платформы Upready Store

Здесь лежит инструкция к панели магазина на платформе Upready Store: где что находится и как сделать
частые дела. Её читают владельцы магазинов и их сотрудники. У каждого шага есть снимок экрана. Снимки
делает скрипт со стенда, и проверка находит снимки, которые устарели после изменения панели.

Источник один, эта папка. Из неё собирается сайт на [VitePress](https://vitepress.dev) со стандартной
темой, и его читают в трёх местах:

| Где читают | Что видно сверху |
|---|---|
| `docs.upready.dev` — документация платформы | знак и название Upready Store |
| адрес документации заказчика, например `docs.cherkashina.ru` | знак и название магазина заказчика |
| `/help/` в панели: пункт «Справка» внизу меню открывает её в новой вкладке на адресе панели | бренд по адресу панели: на `panel.cherkashino.ru` «Черкашино», на остальных Upready Store |

Тексты и снимки у всех одни и те же: ни на странице, ни на снимке нет названия, адреса или людей
конкретного магазина. Меняются только знак и название в шапке.

| Файл | Что в нём |
|---|---|
| [guide/](guide/) | страницы инструкции по-русски, по одной на раздел; кадры подключены как `![…](shots/<id>.webp)` |
| [guide/shots/](guide/shots/) | кадры, WebP без потерь; лежат в git, см. ниже |
| [scenes.mjs](scenes.mjs) | список кадров: роль, адрес экрана, что нажать, что обвести, из какого кода экран нарисован |
| [shoot.mjs](shoot.mjs) | снимает кадры со стенда в `guide/shots/` и пишет `shots.lock.json` |
| [shots.lock.json](shots.lock.json) | с чего снят каждый кадр: хеш кода экрана, хеш его текстов, хеш самого кадра, коммит; и текст, который кадр показывает |
| [check.mjs](check.mjs) | проверка: какие кадры устарели и почему, все ли файлы кадров на месте |
| [publish.mjs](publish.mjs) | собирает сайт VitePress на каждый бренд, с корня и для `/help/`, и таблицу хостов для nginx |
| [.vitepress/config.mjs](.vitepress/config.mjs) | настройки сайта: меню разделов, поиск, русские подписи, бренд сборки |
| [brands.json](brands.json) | таблица брендов: хост → название и логотип |
| [brands/](brands/) | логотипы из таблицы |

## Где живёт документация и почему

Текст, список кадров, кадры и инструменты лежат здесь, в репозитории, рядом с кодом панели. Проверка
свежести сравнивает кадры с кодом того же коммита, поэтому они должны жить вместе.

**Кадры в git.** Справка выкладывается вместе с панелью: образ панели собирает её из этой папки, и
кадры должны быть в том же коммите, что и страницы. Ещё GitHub показывает страницы `guide/` сразу с
картинками. Чтобы история не росла быстро, кадры хранятся в WebP без потерь: те же точки, что в PNG,
а весь набор из 42 кадров весит около 2,3 МБ. Пересъёмка меняет только кадры устаревших экранов.

**На кадрах только условные данные.** Кадры видит любой, кто открыл справку, и все заказчики читают
одни и те же кадры, поэтому на них нет ни настоящих людей, ни настоящего магазина. Магазин стенда
называется «Демо-магазин», его адреса `demo-shop.example`. Логины стенда условные: «Владелица Пример»
owner@example.ru, «Менеджер Анна» manager1@example.ru, «Менеджер Мария» manager2@example.ru,
«Оператор Пример» operator@example.ru. Покупатели обезличены, реквизиты продавца заглушечные, склад
называется «Склад магазина». Две проверки держат это правило:

1. `shoot.mjs` перед снимком читает текст экрана и значения полей. Если там фамилия человека магазина,
   рабочая почта, название магазина-заказчика или его адрес, кадр не снимается, и скрипт называет
   его. Фамилии записаны в [lib.mjs](lib.mjs) хешами, чтобы самих имён в репозитории не было.
   Названия и адреса заказчиков берутся из [brands.json](brands.json): каждое название, кроме
   Upready Store, и имя домена каждого хоста заказчика (`panel.cherkashino.ru` → `cherkashino`; оно же
   стоит в адресах товаров и артикулах). Новый заказчик в таблице сразу попадает под запрет.
2. Текст каждого кадра записывается в `shots.lock.json`, и тест панели
   (`apps/tenant-panel/src/__tests__/owner-guide.test.mjs`) ищет те же слова там. `check.mjs` следит,
   что файл кадра в git тот самый, что снял `shoot.mjs`: хеш файла совпадает с записанным.

**Справка собирается при сборке образа панели.** [Dockerfile](../../apps/tenant-panel/Dockerfile)
панели копирует эту папку и после `vite build` запускает `publish.mjs --out /repo/help-sites`; nginx
отдаёт `/help/` как обычные файлы, а на порту 8081 сборку с корня для адресов документации (ниже).
На сервер при выкладке едет из `docs/` только эта папка (`deploy/scripts/deploy-instance.sh`). Готовой
сборки в git нет: она повторяла бы страницы и кадры, и её пришлось бы пересобирать руками после каждой
правки текста, а забытая пересборка выложила бы старую справку. `vitepress` — пакет панели
(`apps/tenant-panel/package.json`), образ его уже ставит. `publish.mjs` останавливает сборку образа,
если страница показывает кадр, которого нет, а VitePress — если ссылка ведёт на страницу, которой нет.

## Бренды и адреса документации

[brands.json](brands.json) — одна таблица на все виды справки:

```json
{
  "default": { "name": "Upready Store", "logo": "brands/upready.svg" },
  "hosts": {
    "docs.upready.dev": { "name": "Upready Store", "logo": "brands/upready.svg" },
    "docs.cherkashina.ru": { "name": "Черкашино", "logo": "brands/cherkashino.svg" },
    "panel.cherkashino.ru": { "name": "Черкашино", "logo": "brands/cherkashino.svg" }
  }
}
```

Хост, которого нет в таблице, получает `default`. Строка с хостом панели заказчика нужна, чтобы и
`/help/` в его панели шла под его знаком. Логотип — квадратный SVG, PNG или WebP в `brands/`, на
странице он 32×32. Знак Upready — тот же, что `apps/homepage/port/public/favicon.svg`; знак
Черкашино — значок с витрины магазина.

Каждый бренд собирается отдельно: `publish.mjs` собирает сайт по разу на каждое название с логотипом
из таблицы, с корня `/` для адресов документации и с `/help/` для панели, и пишет `brands.map`: какой
хост какую сборку получает. nginx панели выбирает папку по `$host` через `map`, неизвестный хост
получает Upready Store. В браузере ничего не подменяется, поэтому чужой знак не мелькает. Чужих адресов
страница не запрашивает: логотипы лежат в сборке.

На международном сервере адреса документации обслуживает образ панели, отдельного сервиса нет:

- nginx панели ([nginx.conf](../../apps/tenant-panel/nginx.conf)) на порту 8081 отдаёт сборку бренда
  этого хоста с корня `/`;
- контейнер `ingress` ([tenant-ingress-sync.sh](../../deploy/scripts/tenant-ingress-sync.sh)) пишет
  для Traefik файл `mt-docs.yml`: по роутеру и сертификату Let's Encrypt на каждый хост из
  переменной `DOCS_DOMAINS` (через запятую, пример в
  [shipshift.env.example](../../deploy/mt/shipshift.env.example)). Пустая переменная — файла нет.

**Новый заказчик:**

1. Строка в `brands.json` с его хостом документации, логотип в `brands/`; если нужно, ещё строка с
   хостом его панели.
2. Запись DNS: его `docs.<домен>` на адрес международного сервера.
3. Хост в `DOCS_DOMAINS` в env-файле сервера, после того как запись DNS работает, и выкладка.

Проверка `check.mjs --structure` (её запускает и тест панели) падает, если у строки таблицы нет
названия или файла логотипа.

## Как устроена справка

Сайт — стандартная тема VitePress, своей вёрстки нет. Настройки в [.vitepress/config.mjs](.vitepress/config.mjs).

- Одна страница на раздел, адрес — имя файла латиницей: `guide/zakazy.md` открывается как `/zakazy`,
  `guide/index.md` — оглавление. Порядок разделов задаёт `PAGES` в [lib.mjs](lib.mjs).
- У каждого подзаголовка короткий якорь латиницей: `## 4. Подтвердить оплату {#oplata}`, ссылка на
  него из другого раздела — `[раздел 2](zakazy.md#oplata)`. `check.mjs` падает, если у подзаголовка нет
  якоря или ссылка ведёт на якорь, которого нет.
- Компьютер: слева меню разделов, у открытого раздела его подзаголовки; справа «На этой странице».
  Телефон: меню открывает кнопка «Разделы».
- Поиск по всем страницам встроен в сборку, без внешних сервисов. Внизу страницы «Предыдущий раздел» и
  «Следующий раздел». Есть светлая и тёмная тема.
- В шапке знак и название бренда. `noindex`: поисковики справку не индексируют.

```bash
node docs/owner-guide/publish.mjs --out /tmp/help-sites            # все бренды
node docs/owner-guide/publish.mjs --out /tmp/help-sites --only cherkashino
```

Сборка с корня лежит в `/tmp/help-sites/<бренд>/root`. Статический сервер должен отдавать
`<адрес>.html` на `/<адрес>`, как nginx (`try_files $uri $uri.html`).

## Снять кадры

Нужен стенд: бэкенд на обезличенной копии базы
([apps/backend/src/scripts/tenant-only](../../apps/backend/src/scripts/tenant-only/README.md), `--anonymize --verify`)
и панель (`apps/tenant-panel`, `vite`). С живой панели не снимать: на ней настоящие покупатели.
Обезличивание копии не трогает логины магазина и тексты, которые магазин написал сам: страницы,
курсы, уроки. Логины на стенде заводятся заново с условными именами (список выше), а имена людей в
текстах заменяются. Магазин стенда переименовывается в «Демо-магазин»: название, адреса, а в адресах
товаров, категорий и артикулах имя домена магазина заменяется на `demo`. `shoot.mjs` назовёт кадр, где
что-то осталось.

Ещё нужен `cwebp` (`brew install webp`): кадры сохраняются в WebP без потерь.

На стенде нужны три логина магазина (владелец, менеджер, оператор) и файл с id записей, которые
показывают кадры:

```jsonc
{
  "product": "prod_…",          // товар с фотографиями
  "course": "crs_…",            // курс с уроками
  "lesson": "lsn_…",            // урок этого курса
  "orderPack": "order_…",       // оплаченный заказ с доставкой, ещё не собран
  "orderPacked": "order_…",     // собранный заказ, ещё не передан в доставку
  "orderShipped": "order_…",    // заказ в доставке
  "orderPaymentWait": "order_…",// заказ, оплату которого нужно подтвердить
  "orderCourse": "order_…"      // заказ курса, ждёт оплату
}
```

```bash
node docs/owner-guide/shoot.mjs --base http://localhost:5181 \
  --logins <файл с логинами стенда> --ids <файл с id>
```

Кадры ложатся в `guide/shots/`, `shots.lock.json` обновляется. Один Chromium, по вкладке на роль, окно
1440×900, светлая тема, русский язык. Видео и trace не пишутся. Запросы к любому адресу, кроме стенда,
обрываются, и скрипт печатает, сколько их было. `--only 02-orders,02-order-pack` переснимает только
эти кадры. Перед коммитом посмотрите новые кадры глазами.

## Проверка свежести

```bash
node docs/owner-guide/check.mjs
```

Кадр считается устаревшим, если после съёмки изменилось одно из двух:

1. **Код экрана.** Файлы из `sources` сцены плюс меню панели. Проверка называет изменённые файлы
   (`git diff` от коммита съёмки).
2. **Тексты экрана.** Строки `ru.json` с префиксами из `i18n` сцены и строки меню. Проверка называет
   изменённые ключи.

Ещё проверка падает, если страница показывает кадр, которого нет в `scenes.mjs` или в `guide/shots/`,
если сцену не показывает ни одна страница, если в `guide/shots/` лежит кадр, который никто не
показывает, если файл кадра не совпадает с `shots.lock.json` и если папки из `sources` больше нет.

Хеши не видят того, что меняется вне этих файлов: общие стили, обновление зависимостей, данные стенда.
Для этого есть сравнение по кадрам. Снимите кадры заново в отдельную папку, не трогая lock, и сравните
с кадрами в git:

```bash
node docs/owner-guide/shoot.mjs … --out /tmp/guide-now --no-lock --compare docs/owner-guide/guide/shots
```

Скрипт назовёт каждый кадр, где изменилось больше 0,5 % точек. Побайтно кадры не сравниваются: два
снимка одного и того же экрана расходятся в нескольких сглаженных точках. Даты «около 6 часов назад»
на экранах заказов меняются со временем, поэтому такой кадр нужно посмотреть глазами.

В `pr-checks.yml` проверка идёт шагом «Owner guide» с `--warn`: она печатает устаревшие кадры в
журнал проверки запроса, но не блокирует его. Обновить кадры может только тот, у кого есть стенд.
Тест панели при этом запускает `check.mjs --structure`, которому стенд не нужен: пропавший файл кадра
сломал бы сборку образа, поэтому он ловится уже в запросе.

## Когда панель изменилась

1. `node docs/owner-guide/check.mjs` — список устаревших кадров.
2. Переснять их: `shoot.mjs … --only <id,id>`. Кадры в `guide/shots/` и `shots.lock.json` обновятся.
3. Посмотреть новые кадры и поправить текст на странице `guide/`, если шаги стали другими.
4. Новый экран — новая сцена в `scenes.mjs` и ссылка на кадр на странице.
5. Посмотреть справку: `node docs/owner-guide/publish.mjs --out <папка>` и статический сервер.
   Кадры и страницы коммитятся вместе; в панель справка попадёт со следующей сборкой образа.
