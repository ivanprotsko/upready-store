# Отсоединение тенанта в standalone Medusa (7.2)

Автор: W5 (ночь платформы, 11→12.09.2026). Спека, код не пишется. Опирается на экспортный бандл
`upready.tenant-bundle/v1` (owner W3, `docs/multitenancy/tenant-bundle-format.md`), на контракт
`docs/multitenancy/admin-tenants-api-contract.md` §4/§5 и на `@medusajs/*` 2.19.0 в `node_modules`
этого ворктри (версии и наличие workflow проверены по коду, не по памяти — источники ниже).

## 1. Что такое standalone

Standalone — отдельный инстанс Medusa 2.19 (та же версия, что у платформы), со своей БД, своей
родной админкой (`:9xxx/app`, без «Магазины» — этого расширения там нет) и своим деплоем витрины.
Владеет им клиент: свой сервер/хостинг, свои креды, свой домен.

**Что клиент получает:**
- Полноценную родную админку Medusa (Settings, Users, Promotions, всё, что платформенная панель
  сознательно не показывает тенантам).
- Полный контроль над инфраструктурой: может менять план хостинга, провайдера оплаты, добавлять
  собственные модули/расширения.
- Данные физически переезжают в его собственность — платформа их больше не хранит после переноса
  файлов (раздел 4) и переключения DNS (раздел 5).

**Что клиент теряет:**
- Платформенную панель («Магазины» в шапке администратора upready) и всё, что она даёт бесплатно:
  общий рефе́ренс-код, бесплатные обновления Medusa при апдейте платформы, единый биллинг.
- Автоматические обновления — с этого момента патчи/мажорные апгрейды Medusa клиент организует сам
  (или как платная услуга upready).
- Общий backup-контур платформы (правило 42a) — если не купит per-instance бэкап отдельно.

## 2. Шаги переноса — раннбук

Источник данных на каждом шаге — экспортный бандл (`POST /admin/tenants/:id/export` или
`node scripts/tenant-export.mjs <handle>`). Скрипт переноса читает bundle.json один раз и держит
**карту id**: `Map<старый_id, новый_id>` per сущность (`products`, `variants`, `customers`,
`regions`, `categories`, `collections`, `stock_locations`, `shipping_options`), пишет её построчно в
`import-log-<handle>-<date>.jsonl` (не только в памяти — процесс может упасть на середине,
лог позволяет докатить с места обрыва).

| # | Шаг | Как (нативно / вручную-скриптом) | Ремаппинг id |
|---|---|---|---|
| 0 | Провижининг инстанса | Репозиторий-шаблон Medusa 2.19 (тот же, что использует платформа), `.env` (новая БД, новый `COOKIE_SECRET`/`JWT_SECRET`), `medusa db:migrate`, первый админ через `npx medusa user -e <email> -p <pass>` — **всё вручную/скриптом**, Medusa не «импортирует» инстанс целиком. | — |
| 1 | Регионы | `createRegionsWorkflow` (`@medusajs/core-flows`, `region/workflows/create-regions.js` — нативно, нужны страны/валюта/налоговая ставка из `bundle.regions`, это reference-данные, не строки тенанта, см. `tenant-bundle-format.md` «Что означает reference data»). | старый `region_id` → новый |
| 2 | Профиль доставки + склад | `createShippingProfilesWorkflow` → `createStockLocationsWorkflow` → `createLocationFulfillmentSetWorkflow` → `createServiceZonesWorkflow` → `createShippingOptionsWorkflow` (все — `@medusajs/core-flows/dist/fulfillment/workflows/*` и `stock-location/workflows/*`, нативно; вход строится из `bundle.warehouse.stock_locations[0]` — адрес, fulfillment sets, service zones, опции доставки с ценами). | `stock_location_id`, `shipping_option_id` |
| 3 | Категории / коллекции | `createProductCategoriesWorkflow`, `createCollectionsWorkflow` (`core-flows/dist/product-category` и `.../product`, нативно) из `bundle.categories` / `bundle.collections`. | `category_id`, `collection_id` |
| 4 | Товары + варианты + цены | Нативно: `createProductsWorkflow` (`core-flows/dist/product/workflows/create-products.js`) — вызывается скриптом построчно по `bundle.products`, т.к. источник JSON, а не CSV (альтернатива — сконвертировать в CSV и прогнать `importProductsWorkflow`, но это лишний конвертирующий шаг без выгоды: `importProductsWorkflow` асинхронный, двухфазный — «start» + подтверждение через Workflow Engine — см. `artifacts/research/2026-09-11-detach-backup/source-1-import-products-workflow.md`). Ремап `category_id`/`collection_id` из шага 3 при создании. | `product_id`, `variant_id` |
| 5 | Инвентарь | `createInventoryItemsWorkflow` + `createInventoryLevelsWorkflow` (`core-flows/dist/inventory/workflows`, нативно) из `bundle.inventory`, привязка к `stock_location_id` из шага 2 и `variant_id` из шага 4. | `inventory_item_id` |
| 6 | Клиенты | `createCustomersWorkflow` + `createAddressesWorkflow` (`core-flows/dist/customer/workflows`, нативно) из `bundle.customers`. Пароль не переносится (bundle никогда не содержит хеш, см. формат) — клиент получает приглашение сменить пароль или логинится заново через emailpass-регистрацию. | `customer_id` |
| 7 | Файлы | Нет нативного workflow для «скопировать чужой bucket» — **вручную/скриптом**, раздел 4. | — |
| 8 | Заказы | Нативного импорта нет (проверено, раздел 3) — **вручную/скриптом**, ограниченно. | — |

Порядок шагов 1→8 обязателен: 4 зависит от 1–3, 5 от 2 и 4, 8 (если делается) — от 1, 2, 4, 6.

## 3. Заказы

Проверено по коду и докам (не по памяти): в `@medusajs/core-flows` 2.19.0 каталог
`dist/order/workflows` содержит `create-order.js` (создание **одного** заказа, ручной draft-order флоу)
и `export-orders.js` (экспорт), но файла `import-orders*` там нет — при том, что соседние модули
(`product`) отдельно несут `import-products*`. Документация Order-модуля Medusa тоже не описывает
bulk/CSV-импорт заказов (см. `artifacts/research/2026-09-11-detach-backup/source-2-order-module-no-import.md`).
Значит: **нативного способа импортировать историю заказов в новый инстанс нет**.

Варианты:

1. **CSV-архив для клиента** (по умолчанию, входит в цену переноса). Скрипт разворачивает
   `bundle.orders` в плоский CSV/несколько CSV (заказы, позиции, платежи) — годится как бухгалтерский
   архив и для ручного ввода отдельных заказов через родную админку, но НЕ восстанавливает историю
   заказов как живые записи в новой БД (клиент их не увидит в разделе Orders).
2. **Прямой перенос строк БД** — платная услуга. Таблицы (проверено по
   `node_modules/@medusajs/order/dist/models`, пакет `@medusajs/order` 2.19.0): `order`, `order_item`,
   `order_change` (+`order_change_action`), `order_summary`, `address`, `line_item`
   (+`line_item_adjustment`, +`line_item_tax_line`), `shipping_method`
   (+`shipping_method_adjustment`, +`shipping_method_tax_line`), `order_shipping_method`,
   `credit_line`, `transaction`, `claim` (+`claim_item`, +`claim_item_image`), `exchange`
   (+`exchange_item`), `return` (+`return_item`), `return_reason`. Плюс связанные по order id таблицы
   двух других модулей, которые бандл уже разворачивает целиком (см. `tenant-bundle-format.md`,
   раздел `orders`): `@medusajs/payment` (`payment_collection`, `payment`, `refund`, `capture`) и
   `@medusajs/fulfillment` (`fulfillment` + связанные). Перенос — `pg_dump --table=<t> --data-only` по
   каждой таблице с фильтром по `order_id IN (...)` на новую БД той же версии схемы, вручную проверить
   последовательности (id-генераторы Medusa — `ulid`, коллизий не будет) и внешние ключи на
   `customer_id`/`region_id`/`product_id` из шагов 1–6.
3. **Рекомендация**: вариант 1 по умолчанию (входит в базовую цену переноса, раздел 8), вариант 2 —
   отдельная платная услуга по запросу клиента (он редко нужен: заказы — история, не операционные
   данные нового магазина).

## 4. Файлы

`tenants/<id>/` — префикс объектов в текущем bucket (контракт §5). Перенос:

- `rclone copy` (или SDK S3, если rclone недоступен на целевой машине) из
  `s3://<платформенный bucket>/tenants/<id>/` в `s3://<bucket клиента>/` — БЕЗ префикса `tenants/<id>/`
  на новой стороне (это уже не мультитенантный bucket, префикс не нужен клиенту).
- Ремап URL: каждый `product.images[].url` / `variant` thumbnail в бандле указывает на старый публичный
  URL (`<платформенный domain или CDN>/tenants/<id>/…`). Скрипт при выполнении шага 4 раннбука
  (товары) переписывает `url` на новый (`<домен клиента>/<тот же object key без tenant-префикса>`)
  до вызова `createProductsWorkflow`, а не после — правка URL постфактум означала бы второй проход
  по всем товарам.
- Что остаётся на платформе: ничего специально не остаётся — после подтверждённого переноса (раздел
  7) и до `purge_files=true` в `DELETE /admin/tenants/:id` файлы тенанта на платформенном bucket
  считаются архивом переноса, а не рабочими данными; их удаление — обычный soft/hard delete тенанта,
  тем же путём, что и для любого другого закрытия магазина (контракт §4), после согласованного окна
  (раздел 5).

## 5. Домен

- До переноса тенант живёт на технической поддомене платформы (`<handle>.upready.dev` или кастомный
  домен, проксируемый платформой на общий backend — решение о wildcard-прокси относится к 7.4,
  `docs/multitenancy/hosting-spec.md`).
- Перенос: клиент (или upready по его просьбе) заводит DNS-запись (`A`/`CNAME`) на новый деплой,
  TTL записи снижается до **300 с** минимум за 24 часа до переключения (стандартная практика смены
  хостинга, чтобы окно пропагации не растягивалось на дни от старого TTL).
- Окно перекрытия: старый (платформенный) и новый (standalone) инстансы держат идентичные данные
  (бандл на момент шага 0 переноса) одновременно **72 часа** — платформенный инстанс отвечает
  read-only (канал `is_disabled: true`, тот же механизм, что у soft delete, контракт §4, без отзыва
  ключа сразу — иначе витрина 401 раньше времени) до истечения TTL-пропагации на всех резолверах,
  затем платформенный поддомен ретируется (`archived_at` + отзыв ключа, штатный `deleteTenantWorkflow`).

## 6. Что не переносится

- Пароли админов/auth-идентичности — бандл никогда не содержит хеш (формат бандла, раздел `admins`);
  админы standalone-инстанса заводятся заново (приглашение / временный пароль).
- Подключения платёжных провайдеров (Stripe/etc. креды) — секреты, не экспортируются нигде.
- Аналитика платформы (если появится) — платформенная телеметрия, не собственность тенанта.
- Модели контент-страниц/home-config волны 2 панели (`feat/mt-panel-2`) — на этой ветке их нет
  (`bundle.pages` всегда `null`, см. формат бандла); когда появятся на слитой ветке, экспорт/импорт
  дооформляется отдельным пунктом, не эта спека задним числом.
- История заказов как живые записи — раздел 3 (только CSV по умолчанию).

## 7. Приёмка переноса

- **Счётчики.** Для каждой сущности (`products`, `customers`, `orders`-CSV-строк, `categories`,
  `collections`, `inventory`, `stock_locations`) — счётчик на новом инстансе равен
  `manifest.counts` бандла минус явно исключённые в разделе 6 позиции.
- **Витрина.** Страница товара открывается на новом домене (любой товар из бандла, случайная
  выборка ≥3).
- **Чекаут.** Оформление заказа с тестовым платежом на новом инстансе проходит от корзины до
  подтверждения (провайдер оплаты клиента настроен заново — раздел 6).
- **История заказов.** CSV-архив открывается и читаем (раздел 3, вариант 1) либо — если куплен
  вариант 2 — заказы видны в родной админке нового инстанса с тем же количеством строк, что в
  `manifest.counts.orders`.

## 8. Цена и время

Оценка на бандле стенда (`tenant-acme-2026-09-11.json.gz`, товары 9, клиенты 4, заказы 6,
`.ai/progress-w3.md`, `elapsed: 0.34s` — это время ЭКСПОРТА/чтения, не импорта; отдельная оценка
времени импорта ниже помечена как НЕ замерено — экстраполяция по числу workflow-вызовов, не
нагрузочный тест).

| Шаг | Кто | Оценка на стенд-бандле (9 товаров / 6 заказов / 4 клиента) |
|---|---|---|
| 0. Провижининг инстанса | инженер | 30–60 мин (репо-шаблон, `.env`, миграции, первый админ — большей частью сценарий, не с нуля) |
| 1–2. Регионы + склад/доставка | скрипт | < 1 мин (единичные workflow-вызовы, объём не зависит от каталога) |
| 3. Категории/коллекции | скрипт | < 1 мин на стенд-бандле (0 категорий/коллекций у acme); на 50 категорий — доли минуты |
| 4. Товары+варианты+цены | скрипт | ~1 мин на 9 товаров (оценка: каждый `createProductsWorkflow`-вызов — round-trip в БД с несколькими вставками; на стенде не замерено отдельно от экспорта) |
| 5. Инвентарь | скрипт | < 1 мин на стенд-бандле (0 позиций у acme) |
| 6. Клиенты | скрипт | < 1 мин на 4 клиента |
| 7. Файлы | скрипт (`rclone`) | зависит от объёма файлов, не от их числа записей — на стенде `files: 0`, не из чего оценить; для непустого тенанта — пропускная способность `rclone`, обычно секунды на мегабайты |
| 8. Заказы (CSV) | скрипт | < 1 мин на 6 заказов |
| 8. Заказы (DB-copy, платно) | инженер | 1–3 часа инженерного времени (ручная сверка FK, отдельная услуга, не автоматизируется сегодня) |
| Итого автоматизируемая часть | скрипт | единицы минут на бандле такого размера — вся оценка ORDER OF MAGNITUDE, не нагрузочный тест |
| Итого «под ключ» (без DB-copy заказов) | — | ~1–2 часа с учётом провижининга, DNS, ручной проверки (раздел 7) |

Оценка НЕ линейно масштабируется на крупных тенантов без отдельного замера (провижининг и DNS —
фиксированные, товары/клиенты/заказы — растут пропорционально бандлу); на бандл в 1000 товаров и
10 000 заказов формула из `backup-spec.md` §3 даёт ориентир по размеру, но не по времени импорта —
это отдельный замер, не сделанный тонight.
