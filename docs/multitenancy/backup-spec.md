# Бэкап данных тенанта (7.3)

Автор: W5 (ночь платформы, 11→12.09.2026). Спека, код не пишется. Опирается на `exportTenantWorkflow`
(owner W3), `docs/multitenancy/tenant-bundle-format.md`, дома́шние правила бэкапов (`~/r/42a.md`,
`~/r/42d.md`, `~/upready/memory/feedback_backup_strategy.md`) и на реальный замер бандла стенда
(`artifacts/deliverables/tenant-exports/tenant-acme-2026-09-11.json.gz`, разобран построчно ниже).

## 1. Ярусы

Действующий бэкап платформы (правило 42a, полный текст `~/r/42a.md`) — три яруса, без исключений:

1. `<project>/backups/` — 7 дней.
2. `~/upready/backups/<project>/` — 30 дней.
3. R2/`restic` (encrypted) — 90 дней + monthly-снапшот, провайдер по умолчанию Cloudflare R2 (42d),
   политика `restic forget --keep-daily 7 --keep-weekly 4 --keep-monthly 12 --keep-yearly 5`.

Этот контур бэкапит **всё** (вся БД + весь bucket файлов, `memory/feedback_backup_strategy.md`:
«Postgres dump — вся пользовательская/контентная БД», «Docker volumes (raw) — uploads/кэши») и
восстанавливает платформу целиком на любой момент снапшота.

**Per-tenant бэкап — четвёртый, ЛОГИЧЕСКИЙ ярус поверх, не замена.** Он даёт то, чего три яруса выше
не дают:
- восстановление ОДНОГО тенанта без разворачивания всего платформенного снапшота;
- откат одного тенанта на дату N дней назад, пока остальные не трогаются;
- переносимый артефакт для detach (`detach-spec.md`) и для клиента как «выгрузка моих данных».

**Важная граница, которую нельзя стереть:** бандл `exportTenantWorkflow` несёт байты файлов
**НЕ во всех случаях** — поле `files` в бандле (см. `tenant-bundle-format.md`) — это список
`{ key, url, size }` из `listTenantFiles()`, метаданные объектов, а не их содержимое. Байты картинок
и файлов тенанта восстанавливает ТОЛЬКО платформенный ярус 3 (весь bucket, restic → R2), не
per-tenant JSON-бандл. Раздел 4 ниже разводит это по сценариям.

## 2. Схема

**Job:** `src/jobs/tenant-backup-nightly.ts` (Medusa scheduled job, `apps/backend/src/jobs/README.md` —
стандартный `export const config = { name: "tenant-backup-nightly", schedule: "0 19 * * *" }`).

Cron-поле у Medusa (проверено по `src/jobs/README.md` — конфиг несёт только `name`, `schedule`,
`numberOfExecutions`) **не знает часовых поясов** — время исполнения = время процесса. `0 19 * * *`
здесь означает 03:00 UTC+8 **при условии, что процесс backend'а работает в TZ=UTC** — это решение
о часовом поясе сервера относится к 7.4 (`hosting-spec.md`); до его принятия число в cron-строке —
предположение, а не факт.

**Что делает job**, для каждого тенанта где `metadata.archived_at == null` (не архивные — архивные
уже застыли, бэкапить нечего нового):

1. `exportTenantWorkflow.run({ input: { handle: tenant.handle } })` — тот же workflow, что использует
   ручной экспорт (A3), без изменений.
2. Сериализация → gzip → запись `backups/tenants/<tenant_id>/<YYYY-MM-DD>.json.gz` в
   `R2_BACKUP_BUCKET` (проверено — переменная уже существует в `~/upready/.env.keys`, это бакет
   платформенного яруса 3, не бакет файлов тенантов).
3. Manifest-файл того же прогона рядом: `backups/tenants/<tenant_id>/<YYYY-MM-DD>.manifest.json`
   (копия `manifest.counts`/`manifest.bytes` бандла + `status: "ok"`), чтобы восстановление и
   проверка (раздел 5) не разжимали gzip только ради счётчиков.
4. Ретенш‑проход (тот же или отдельный job `tenant-backup-retention`, следующим шагом за первым):
   листинг `backups/tenants/<tenant_id>/` по датам, оставить последние 30 ежедневных +
   по одному первому числу месяца за 12 месяцев, остальное удалить.

**Решение о размещении в R2 — `backups/tenants/<id>/…`, отдельный корень, НЕ под `tenants/<id>/`
файлового бакета.** Причина: файловый префикс `tenants/<id>/` — это ровно то, что стирает
`deleteTenantFilesStep` при `purge_files=true` (контракт §4/§5). Если бы бэкапы лежали под тем же
префиксом (даже в другом бакете), это было бы концептуальной путаницей «бэкап живёт там же, где
данные, которые он должен пережить»; кладя их в отдельный, уже существующий R2-бакет платформенного
яруса 3 с отдельным корнем `backups/`, бэкап тенанта переживает purge файлов тенанта по конструкции,
а не по счастливой случайности бакета.

**Отказ (`status: "failed"` в manifest'е job'а):** в кодовой базе backend'а сейчас **нет** готового
канала алертов (проверено: `grep -rl discord` по `apps/backend/src` — пусто; `DISCORD_TOKEN` в
`~/upready/.env.keys` принадлежит другому инструменту, в backend не подключён). Решение на сегодня:
`logger.error(...)` (framework-логгер, попадает в лог процесса/контейнера) + запись
`backups/_failures/<YYYY-MM-DD>/<tenant_id>.json` с текстом ошибки, которую сможет читать монитор
7.4, когда появится хостинг с системой алертов. Живой пуш-канал (Discord/email) — не сегодняшняя
задача, это не развилка (альтернативы для «сегодня» нет — канала физически не существует), а прямое
следствие того, что 7.4 ещё не решён.

## 3. Размер и время

Замер на стенде — реальный, не оценка: `tenant-acme-2026-09-11.json.gz`
(`.ai/progress-w3.md`, `docs/multitenancy/tenant-bundle-format.md`), счётчики
`admins=1 products=9 inventory=0 categories=0 collections=0 customers=4 orders=6 regions=1 files=0
stock_locations=1`, `bytes (uncompressed) = 48886`, `bytes (gzip) = 11433`, `elapsed = 0.34s`.

Разбор бандла по секциям (разжатый `tenant-acme-2026-09-11.json.gz`, посчитано
`Buffer.byteLength(JSON.stringify(bundle[key]))` для каждого ключа):

| Секция | Байт | На единицу |
|---|---|---|
| `warehouse` (1 stock_location) | 33 252 | фиксировано на тенанта (1 склад на этой ветке — `provisionTenantWarehouseWorkflow`) |
| `orders` (6) | 7 744 | ~1291 байт/заказ |
| `products` (9) | 5 799 | ~644 байт/товар |
| `customers` (4) | 1 029 | ~257 байт/клиент |
| `api_key` | 164 | фикс |
| `manifest` | 162 | фикс |
| `regions` (1) | 119 | ~119 байт/регион |
| `admins` (1) | 108 | ~108 байт/админа |
| `tenant` | 85 | фикс |
| `source` | 73 | фикс |
| `sales_channel` | 72 | фикс |
| `format`/`exported_at`/`pages`/пустые (`inventory`/`categories`/`collections`/`files`) | 62 | фикс |

**`inventory`/`categories`/`collections`/`files` на стенде равны нулю** (реальное состояние acme,
объяснено в `tenant-bundle-format.md`), поэтому байт/единицу для них измерить НЕЧЕМ — этого числа в
спеке нет, потому что его неоткуда взять, а не потому что забыли.

**Формула** (json, без сжатия), при типовых `admins=2`, `regions=1`, `stock_locations=1`,
клиенты ≈ 0.667×заказов (соотношение бандла acme, 4/6):

```
bytes_json(P, O) ≈ 34 207 + 644×P + 1462×O
```

где `34 207` = фикс + `warehouse` + 2 админа + 1 регион, `1462` = 1291 (заказ) + 257×0.667 (доля
клиента на заказ). Гзип на стенде даёт коэффициент `11433 / 48886 = 0.234` — тот же коэффициент
применён ниже; структура данных однородная (повторяющиеся объекты), так что коэффициент не должен
сильно плыть с размером, но это тоже не измерено на большем бандле, а перенесено с одной точки.

| Товаров | Заказов | bytes_json | bytes_gz (×0.234) |
|---|---|---|---|
| 10 | 0 | ~40.6 KB | ~9.5 KB |
| 10 | 1 000 | ~1.50 MB | ~0.35 MB |
| 10 | 10 000 | ~14.7 MB | ~3.4 MB |
| 100 | 0 | ~98.6 KB | ~23 KB |
| 100 | 1 000 | ~1.56 MB | ~0.37 MB |
| 100 | 10 000 | ~14.7 MB | ~3.4 MB |
| 1 000 | 0 | ~678 KB | ~159 KB |
| 1 000 | 1 000 | ~2.14 MB | ~0.50 MB |
| 1 000 | 10 000 | ~15.3 MB | ~3.4 MB |

**Время** — ТОЛЬКО оценка, не замер под нагрузкой: 0.34с на стенде покрыли 22 «строки»
(9 товаров + 6 заказов + 4 клиента + 1 админ + 1 регион + 1 склад) — наивная линейная модель
(`22 / 0.34с ≈ 65 строк/с`) даёт:

| Товаров | Заказов | Оценка времени (линейная, НЕ нагрузочный тест) |
|---|---|---|
| 10 | 0 | ~0.2 с |
| 100 | 1 000 | ~27 с |
| 1 000 | 10 000 | ~4.6 мин |

Эта модель предполагает, что `query.graph`-обход растёт линейно с числом строк — на 22 строках это
не проверить, реальная зависимость может быть хуже линейной (JOIN-сложность, память) при 10 000+
заказов. **Перед тем как полагаться на ночной job для тенанта такого размера — нужен отдельный замер
на бандле в 1000+ заказов**, это не сделано сегодня и не должно читаться как сделанное.

## 4. Восстановление

Восстановление = импорт бандла в ТОТ ЖЕ инстанс (raннбук `detach-spec.md` §2, БЕЗ шага 0 —
провижининга — инстанс уже есть), с семантикой **replace = upsert по оригинальному id, никогда не
wipe-then-insert**. Это принципиально: на том же инстансе id из бандла совпадают с id в текущей БД
(это не detach в новый инстанс, где id перевыпускаются), поэтому «заменить» товар/клиента/заказ —
значит обновить существующую строку значениями из бандла, а НЕ удалить весь набор сущностей тенанта
и вставить заново — иначе восстановление случайно стирает легитимные строки, созданные ПОСЛЕ
бэкапа.

Семантика replace по сущностям:
- **products/variants/prices** — upsert по id из бандла (нативных «restore»-workflow нет — сценарий
  ближе к detach-раннбуку шага 4, но с `updateProductsWorkflow`/`upsert` вместо `create`, когда id
  уже существует).
- **inventory** — upsert `stocked_quantity`/`reserved_quantity` по `location_levels` бандла.
- **customers** — upsert контактных данных/адресов; пароли не трогаются (бандл их не несёт).
- **orders** — restore заказов = тот же вывод, что в `detach-spec.md` §3: нативного импорта нет,
  восстановление истории заказов из per-tenant бэкапа — это чтение CSV-архива вручную, не
  автоматический upsert (риск переиграть платёжный/fulfillment-граф вслепую — заказ не «просто
  строка», у него собственный workflow-движок изменений).
- **files** — см. раздел 1: бандл несёт только список `{key,url,size}`, не байты. «Восстановить
  файлы из per-tenant бэкапа» физически невозможно этим артефактом — байты идут из платформенного
  яруса 3 (restic → R2 всего bucket). Per-tenant бэкап здесь полезен только как **сверочный список**
  (раздел 5): какие ключи должны существовать.

**Случай soft-deleted тенанта** (`DELETE /admin/tenants/:id` без `purge_files`, контракт §4),
случайное удаление — что нужно откатить:

1. **Un-archive**: `tenant.metadata.archived_at = null` (тот же module service, `updateTenants`,
   что использует шаг 1 `deleteTenantWorkflow` — но не через compensation воркфлоу, компенсация
   срабатывает только внутри падающего запуска; здесь нужен отдельный маленький «un-archive» шаг/
   скрипт, вызывающий ту же module-service-функцию в обратную сторону).
2. **Канал**: `updateSalesChannelsWorkflow.runAsStep({ is_disabled: false })`.
3. **Ключ**: публикуемые ключи **нельзя «раз-отозвать»** — проверено по
   `@medusajs/types` 2.19.0 (`api-key/mutations/api-key.d.ts`): `UpdateApiKeyDTO` несёт только
   `title`, никакого поля для снятия `revoked_at`; отдельного un-revoke workflow в `core-flows` нет.
   Значит восстановление ключа — это **новый** ключ (`createApiKeysWorkflow` + линковка к тенанту,
   тот же путь, что при первом создании тенанта), а не реанимация старого. Практическое следствие:
   витрина/интеграции тенанта, у которых старый публикуемый ключ зашит в конфиг, должны получить
   новый — это не развилка (альтернативы физически нет), а операционный шаг восстановления, который
   нужно проговорить с клиентом заранее.
4. **Вход админов**: закрывается мидлварью по `archived_at` (контракт §4) — шаг 1 автоматически
   открывает его обратно, отдельного действия не требуется.
5. **Файлы**: при `purge_files=false` (дефолт) — ничего восстанавливать не нужно, объекты никуда не
   делись (контракт §4, шаг 4 delete-workflow вообще не выполнялся). При `purge_files=true` — байты
   не восстановимы per-tenant бэкапом (раздел 1); единственный путь — платформенный ярус 3
   (restic-снапшот бакета на дату до удаления), отдельная операция вне этой спеки.

## 5. Проверка бэкапа

Ежемесячный restore drill в одноразовую БД: интеграционный раннер (`@medusajs/test-utils`,
`node_modules/.pnpm/@medusajs+test-utils@2.19.0.../dist/database.js`) уже умеет поднимать и сносить
одноразовую БД программно (`createDatabase`/`dropDatabase` из `medusa-test-runner-utils`, тот же
механизм, что использует `pnpm test:integration:http` для каждого прогона) — drill переиспользует
этот механизм, не пишет свой.

Шаги: раз в месяц (cron/ручной запуск) — поднять throwaway БД → прогнать `medusa db:migrate` на ней
→ восстановить один случайный НЕ-архивный тенант из его последнего ночного бэкапа по раннбуку
раздела 4 (в create-режиме, т.к. throwaway БД пуста — фактически это detach-раннбук §2 без шага 0,
не restore-upsert, потому что restore-upsert по определению требует существующих строк) → сверить
`manifest.counts` бэкапа с фактическими счётчиками на throwaway БД → снести БД.

**Приёмка** = совпадение счётчиков; расхождение — сигнал, что либо `exportTenantWorkflow`, либо
импорт-раннбук сломан молча, раньше, чем это обнаружится на реальном инциденте.

## 6. Развилки

Развилок нет — оба решения в разделе 2 (место в R2, формат job'а) и в разделе 4 (upsert-семантика,
переиздание ключа вместо un-revoke) приняты и обоснованы фактами кода/правил выше, альтернатив,
которые стоило бы отдавать Ивану на утро, не осталось. Единственное, что действительно ждёт
внешнего решения — часовой пояс сервера для cron-строки (раздел 2) и живой канал алертов (раздел 2)
— но это не развилки ЭТОЙ спеки, а прямые следствия ещё не решённого 7.4 (`hosting-spec.md`),
дублировать вопрос здесь не нужно.
