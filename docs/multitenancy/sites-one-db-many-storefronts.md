# Одна база — несколько сайтов одного клиента (дизайн-решение)

Заказ Ивана 22.09.2026 (olavka.com / olavka.ru, клиент тот же, что cherkashino):

> база данных должна быть одна, но будут различия … один сайт с DHL + Почта России
> + СДЭК и товарами cherkashino, второй — Почта России + СДЭК и весь каталог
> Wildberries … дизайн общий … должен быть раздел, где создаются 2-я/3-я версия
> сайта, и у сущностей переключатель «везде / на выбранных сайтах».

Автор — ведущий инженер заказа olavka (ветка `feat/olavka-sites`). Статус:
**решение принято, реализация по шагам §5; шаги 0–1 выполнены 22.09.**

## 1. Решение одной строкой

**Сайт = тенант. Клиент = группа тенантов. Общий каталог — через родные
`product_sales_channel` Medusa, а не через копирование товаров.** Никакого
отдельного «конфига сайтов» поверх одного тенанта не заводим.

## 2. Почему так (и что отвергнуто)

Что уже есть per-tenant и ровно совпадает с «различиями между сайтами» из
заказа: домены и handle (`tenant_domain`, `tenant_handle_alias`), язык/страна
(`tenant_locale_settings`), тема и главная (`tenant_home_config`), склад +
методы доставки с тарифами (`stock_location` → `fulfillment_set` →
`shipping_option`, см. `apps/backend/src/api/tenants/shipping-methods/helpers.ts:54`),
оплата (`tenant_integration_secret` provider=robokassa), уведомления,
страницы, редиректы, реквизиты, ключи маркетплейсов (WB/Ozon — per tenant,
`wb_product.tenant_id`). Заказы тоже уже приземляются на тенант по
`order.sales_channel_id` (`subscribers/order-placed-tenant-link.ts`).

Значит, второй сайт как второй тенант получает *все* переключаемые различия
бесплатно. Не хватает трёх вещей: (а) понятия «эти тенанты — один клиент»,
(б) общего каталога без дублирования товаров, (в) кнопки «создать сайт-копию».

Отвергнуто:

- **«Маленький конфиг сайтов» внутри одного тенанта** (per-host overrides
  чекаута/навигации/фич в JSON). Пришлось бы заново придумывать per-host
  доставку, оплату, локаль, заказы, SEO-канонику, домены — всё это в тенанте
  уже сделано. Двойная машинерия.
- **Отдельная БД на сайт.** Прямо против «база данных должна быть одна».
- **Копирование товаров во второй тенант.** Ломает «товар один, показывается на
  выбранных сайтах»: цена/остаток/фото разъезжаются, WB-синк не знает, какой из
  двух — настоящий.

## 3. Целевая модель

### 3.1 Группа клиента

Новая модель `tenant_group` (`tgrp_…`: `id`, `name`, `metadata`) и поле
`tenant.group_id` (nullable — одиночные магазины ничего не замечают). Группа
создаётся неявно первой кнопкой «Создать сайт» у тенанта без группы.

Панель: у владельца одна учётка на группу. Сейчас `tenant_admin.email`
уникален глобально и админ привязан ровно к одному тенанту — поэтому первая
итерация даёт **переключатель сайта** без второй учётки:
`POST /tenants/switch/:tenantId` выдаёт JWT на другой тенант **той же группы**
(проверка `tenant.group_id` совпадает; иначе 404 — чужой тенант не существует,
как везде в `/tenants/*`). До этого шага — отдельный логин на сайт (работает
уже сегодня).

### 3.2 Общий каталог: владелец один, показ — по каналам

- **Владение** товаром остаётся у одного тенанта (link
  `tenant_tenant_product_product`, `apps/backend/src/links/tenant-product.ts`);
  link-сервис Medusa всё равно не даёт второго владельца.
- **Видимость** = `product_sales_channel` (родная many-to-many). Витрина уже
  фильтрует по publishable key → sales channel (`by-host` → `x-publishable-api-key`),
  так что товар, добавленный в канал второго сайта, появляется там без единой
  строчки на витрине.
- Переключатель у товара: **«везде»** = товар состоит во всех каналах группы;
  **«на выбранных сайтах»** = подмножество. Хранится не отдельным флагом, а
  фактом состава каналов; UI считает «везде», когда набор = все каналы группы.
  Новый сайт, созданный в группе, по умолчанию получает все товары со значением
  «везде» (шаг клона добавляет свой канал к таким товарам).
- Изменение в `tenant-scope.ts` (`listTenantProductIds`, сейчас: «товар в канале
  тенанта, но не созданный им, сюда не попадает»): для тенанта с `group_id`
  читать товары **всех тенантов группы** (read/visibility), а запись
  (цена, фото, атрибуты) — только через тенанта-владельца либо через
  переключатель сайта §3.1. Корзины/чекаут не меняются: `validate-cart-sales-channel`
  уже проверяет, что товар в канале сайта.

### 3.3 Переключатель «везде / на выбранных» у не-товарных сущностей

Локаль по умолчанию, валюта (страна → регион), страницы, редиректы,
уведомления — это per-tenant строки, «общими» они быть не могут. Поэтому
переключатель здесь — **действие при сохранении**: «применить ко всем сайтам
группы» = fan-out того же upsert-workflow по тенантам группы;
«только на этот сайт» = как сейчас. Выбор запоминается в `metadata.site_scope`
сущности только для памяти UI. Никакой «наследуемой» настройки с дырами —
после сохранения каждая строка самодостаточна, витрина и `by-host` не меняются.

### 3.4 Раздел панели «Сайты»

Группа `settings` в `apps/tenant-panel/src/components/layout/owner-nav/nav-model.ts`,
маршрут `/settings/sites`: список сайтов группы (handle, домены, primary,
статус сертификата), кнопка **«Создать сайт»** → workflow `clone-tenant`
(`apps/backend/src/workflows/tenant/clone-tenant/`):

1. `createTenantWorkflow.runAsStep` — новый handle, свой sales channel,
   publishable key, склад и базовая зона (как сейчас у `create-tenant`).
2. Копия строк: `tenant_locale_settings`, `tenant_home_config` (тема + главная),
   `tenant.metadata.branding/analytics/shipping_default_weight_g`,
   `tenant_requisites`, `tenant_notification_settings`, `tenant_product_attribute*`,
   `tenant_page` (по флагу), методы доставки с тарифами (`shipping_option` +
   `data`) — по флагу «скопировать доставку».
3. **Не копируются**: `tenant_integration_secret` (ключи WB/Ozon/СДЭК/Robokassa
   вводятся на сайте заново — у второго сайта они свои), домены, заказы,
   редиректы, `tenant_handle_alias`.
4. Товары «везде» получают канал нового сайта (§3.2).
5. `tenant.group_id` = группа исходного (создать при отсутствии).

Опора для копирования — уже существующий read-only экспорт
`export-tenant` (`upready.tenant-bundle/v1`, `docs/multitenancy/tenant-bundle-format.md`):
клон = экспорт-бандл без секретов/товаров → импорт в новый тенант.

### 3.5 Заказы

Как сейчас: заказ принадлежит сайту, на котором оформлен. Сводка по группе —
позже, `GET /tenants/orders?scope=group` (объединение по `tenant.group_id`).

| | olavka.com (сайт 1) | olavka.ru (сайт 2) | cherkashino.ru (сайт 3, только числится) |
|---|---|---|---|
| тенант | `ten_01M2GQVGEN1204CN90C510DNRG` (бывш. cherkashino; handle → `olavka`) | новый, клон сайта 1 | новый, клон; handle `cherkashino` — сейчас зарезервирован алиасом после переименования, перед созданием алиас снять |
| домены | olavka.com, www.olavka.com (**сделано 22.09**) | olavka.ru, www.olavka.ru — A-запись на 84.46.251.149 у reg.ru ставит Иван | cherkashino.ru |
| доставка | DHL (carrier `dhl`, новый), Почта России (`post_ru`), СДЭК (API) — **сделано 22.09**, тарифы-заглушки | Почта России + СДЭК | ApiShip + СДЭК (интеграции) |
| оплата | крипта + карта через менеджера (по материалам агента olavka-payments-shots); до готовности — `pp_system_default` «Оплата вручную» | те же | Robokassa |
| вход покупателя | e-mail | e-mail | Yandex ID |
| каталог | товары cherkashino (владелец — этот тенант) | **весь каталог WB клиента** | по решению Ивана |
| дизайн | общий: клон копирует `tenant_home_config` + branding | | |

Из третьего сайта для модели следует: **провайдеры оплаты, входа и доставки —
per-site**, и это уже так: Robokassa — `tenant_integration_secret`
provider=robokassa (+ `pp_system_default` везде), ApiShip/СДЭК — те же
секреты provider=apiship/cdek, методы доставки — per-tenant `shipping_option`.
Yandex ID как способ входа покупателя на платформе нет — это новый auth-провайдер
с per-tenant client_id/secret (`tenant_integration_secret` provider=yandex_id)
и включением в `tenant.metadata.auth_providers`; заводится, когда дойдёт
очередь сайта 3. Существующие пути Robokassa/CDEK/ApiShip в коде не трогаются
ни одним шагом §5.

**Каталог WB для сайта 2 — отдельная работа.** Сегодня WB-карточка *не становится*
товаром: `wb_product` → `mp_product` → `autoLink` по `vendorCode` = `product_variant.sku`
(`apps/backend/src/modules/marketplace/`). Нужен workflow `import-products-from-wb`
(карточка → продукт: название, фото, цена, SKU `<nmID>-…`, категория) с
привязкой к владельцу-тенанту и к каналу сайта 2. Ключ WB у клиента на платформе
уже есть (`tenant_integration_secret` provider=wildberries, 423 карточки в
`wb_product`) — по группе его можно переиспользовать без повторного ввода,
если Иван решит, что WB-кабинет один на группу (§3.4 п.3 тогда получает
исключение «ключи WB — групповые»).

## 5. Порядок реализации

0. **Сделано 22.09:** olavka.com как домен тенанта cherkashino на живой
   платформе; DHL как carrier (`apps/backend/src/shipping-tariffs/carriers.ts`,
   коммит `bcc0df5f`); методы Почта России/DHL; Курьером/Самовывоз выключены.
1. **Сделано 22.09:** этот документ.
2. `tenant_group` + `tenant.group_id` + миграция; `POST /tenants/switch/:id`.
3. `tenant-scope.ts`: чтение товаров по группе; PATCH товара — поле
   `site_scope: "all" | { tenant_ids }` → пересчёт `product_sales_channel`.
4. Workflow `clone-tenant` + раздел панели «Сайты».
5. Fan-out «применить ко всем сайтам» у локали/страниц/уведомлений.
6. `import-products-from-wb` для olavka.ru; создание сайта 2 клоном; домены olavka.ru.

Каждый шаг — отдельный PR с `pnpm check:backend-build` (AGENTS.md). Ничего из
2–6 не требует остановки живых магазинов: только новые таблицы/поля и
новые роуты.
